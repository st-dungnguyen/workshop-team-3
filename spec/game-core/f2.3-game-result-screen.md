# Feature PRD: F2.3 — Game Result Screen

## 1. Feature Name

**Game Result Screen** — A shared win/lose result screen displayed after the game animation completes, presenting the outcome to the player and directing them to the appropriate next action.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

After the game variant finishes its reveal animation (F2.2), the result screen takes over to clearly communicate the outcome. This screen is shared across all game variants — Lucky Wheel, Scratch Card, and any future variants all use the same result screen. The win path triggers the reward flow ([E3](../reward-coupon/_epic-E3-reward-coupon.md)); the lose path gives the player a clear next step.

The result screen is the emotional peak of the player's experience: a win should feel rewarding and celebratory; a lose should be warm and encouraging — not punishing.

**Intended Audience:** Engineering team.

**Assumptions:**
- The result screen receives the outcome (`win` or `lose`) from the game shell (F2.2) after the animation completes.
- On a win, the result screen is responsible for initiating the reward flow handoff to E3. It does not issue the coupon itself.
- On a lose, there is no retry within the same session. Play limits are enforced by E4.
- All result screen text must be in both `ja` and `en` (`game.json` namespace).
- The result screen is the same regardless of which game variant was played.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Has just seen their outcome revealed; now needs to understand what they won (or didn't), and what to do next |

## 5. User Stories

- As a **PLAYER who won**, I want to see a clear confirmation of my win and a direct path to claim my coupon so that I don't have to figure out what to do next.
- As a **PLAYER who lost**, I want a friendly, encouraging message so that I don't feel discouraged from coming back to the app in the future.
- As a **PLAYER**, I want the result screen to feel thematically consistent with the game so that the experience doesn't feel disjointed.

## 6. Requirements

### Functional Requirements

**Win state**

- **REQ-301**: When the session outcome is `win`, the system shall display the win result screen with a visually prominent win indicator (e.g., celebratory illustration, positive message) and a visual representation of the coupon reward.
- **REQ-302**: The win result screen shall display two primary CTAs that together initiate the reward flow defined in [E3](../reward-coupon/_epic-E3-reward-coupon.md):
  - **"Claim Coupon"** (`reward.claimCoupon`) — saves the coupon and navigates the player to the coupon detail screen in the native app.
  - **"Use Now"** (`reward.useNow`) — applies the coupon and navigates the player directly to the takeout ordering screen in the native app with the coupon pre-applied.
  Both CTAs trigger the same win-recording API call (F3.1) before navigation — the difference is the AppLink destination (F3.2).
- **REQ-302a**: When the Scratch Card variant is active, the win result screen shall additionally display a tertiary CTA: **"View Coupon List"** (`reward.viewCouponList`) — navigating the player to the native app's coupon screen via AppLink. This CTA does **not** trigger the win-recording flow and navigates outside the WebView. The "View Coupon List" CTA is absent when the Flip Card variant is active.
- **REQ-303**: The win result screen shall not display the coupon's full detail (name, discount amount, expiry) itself — the coupon type and visual tier (e.g., "200円OFF") shall be shown as a preview only; the full coupon detail is shown in the native app after AppLink navigation.
- **REQ-304**: If the reward flow (E3) fails (backend unavailable), the win result screen shall display a `reward.claimError` state with a retry option — the player must not be left with a win confirmation but no path to claim it.

**Lose state**

- **REQ-311**: When the session outcome is `lose`, the system shall display the lose result screen with a warm, friendly message — the tone must be encouraging, not punishing.
- **REQ-312**: The lose result screen shall display a CTA to close the WebView and return to the native app.
- **REQ-313**: The lose result screen shall not offer a replay option within the same session. Whether the player can play again (next day, next window) is communicated by E4.

**Shared behavior**

- **REQ-321**: The result screen shall appear immediately after the variant signals animation completion — there shall be no blank or loading state between the animation end and the result screen appearing.
- **REQ-322**: All player-facing strings on the result screen must be available in `ja` and `en` via the `game.json` i18n namespace.
- **REQ-323**: The result screen layout and visual style shall be consistent with the warm Japanese food-brand aesthetic and the active game variant's visual theme.

### Constraints

- **CON-301**: The result screen is shared across all game variants. It must not contain variant-specific logic or visual elements (those belong to the variant itself, not the result screen).
- **CON-302**: Both win CTAs ("Claim Coupon" and "Use Now") must always trigger E3 — the result screen must not navigate directly to any AppLink. The AppLink navigation is E3's responsibility after coupon issuance. The CTA selection is passed to E3 so it knows which AppLink to navigate to.
- **CON-303**: Both CTAs must be disabled while the win-recording request (F3.1) is in flight. They must not be tappable until E3 either succeeds (navigating away) or fails (showing the retry state).

### Guidelines

- **GUD-301**: The win state should use celebratory visual elements appropriate to the Japanese aesthetic (e.g., confetti, decorative motifs, warm gold tones) without being excessive.
- **GUD-302**: The lose state message should align with the seasonal campaign tone — for example, "また明日チャレンジしよう！" (Try again tomorrow!) rather than a generic "You lost."
- **GUD-303**: On the win screen, "Use Now" should be the visually primary CTA (filled/prominent) and "Claim Coupon" the secondary CTA (outlined/subdued) — the business goal is to convert the coupon to an order, not just to save it.
- **GUD-304**: All CTAs (both win and lose screens) must have a minimum touch target of 44px height.

## 7. Acceptance Criteria

**Win path**

- **AC-301**: Given the game outcome is `win` and the animation has completed, when the result screen appears, then a win confirmation message, a coupon visual, a "Claim Coupon" CTA, and a "Use Now" CTA are all visible.
- **AC-301a**: Given the Scratch Card variant is active and the outcome is `win`, when the result screen appears, then a third "View Coupon List" CTA is also visible in addition to "Claim Coupon" and "Use Now".
- **AC-301b**: Given the Flip Card variant is active and the outcome is `win`, when the result screen appears, then only "Claim Coupon" and "Use Now" are shown — no "View Coupon List" CTA.
- **AC-302**: Given the win result screen is shown, when the player taps either "Claim Coupon" or "Use Now", then both primary CTAs are disabled and the reward flow (E3) is initiated with the selected CTA intent.
- **AC-302a**: Given the win result screen is shown (Scratch Card), when the player taps "View Coupon List", then the native app's coupon screen is opened via AppLink — no win-recording request is sent by this action.
- **AC-303**: Given E3 fails to issue the coupon (backend 500/503), when the player is on the win result screen, then a `reward.claimError` message appears with a retry button — the win confirmation and coupon visual remain visible.
- **AC-304**: Given E3 successfully issues the coupon and the player tapped "Claim Coupon", then the player is navigated to the segment coupon detail screen in the native app via AppLink.
- **AC-305**: Given E3 successfully issues the coupon and the player tapped "Use Now", then the player is navigated to the takeout ordering screen with the coupon pre-applied via AppLink.
- **AC-306**: Given a CTA is tapped and the win-recording request is in flight, when the player taps the other CTA, then no additional request is sent (both CTAs disabled until response).

**Lose path**

- **AC-311**: Given the game outcome is `lose` and the animation has completed, when the result screen appears, then a friendly lose message and a "Close" CTA are visible — no replay button is shown.
- **AC-312**: Given the lose result screen is shown, when the player taps the close CTA, then the WebView navigates to `{webViewHost}/close`.

**Shared behavior**

- **AC-321**: Given the animation completes (either variant), when the result screen appears, then no blank or loading state is observed between animation end and result display.
- **AC-322**: Given the result screen is displayed, when the locale is `ja`, then all text is in Japanese; when the locale is `en`, then all text is in English.
- **AC-323**: Given the active variant is Lucky Wheel vs. Scratch Card, when both produce a `win` outcome, then the same result screen layout is shown in both cases.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Win flow — "Claim Coupon":** Animation completes with `win` → result screen shows coupon visual + two CTAs → player taps "Claim Coupon" → CTAs disabled → E3 initiates → AppLink to coupon detail.
- **Win flow — "Use Now":** Same as above but player taps "Use Now" → AppLink to takeout screen with coupon pre-applied.
- **Lose flow — full:** Animation completes with `lose` → result screen appears immediately → friendly message shown → player taps close → WebView closes.
- **Win with E3 failure:** Win result shown → player taps a CTA → backend 500 → `reward.claimError` shown with retry → retry succeeds → AppLink navigation.
- **Double-tap prevention:** Player taps a CTA twice or taps both CTAs quickly → only one win-recording request sent, both CTAs remain disabled.
- **Transition timing:** No gap or blank state between animation end and result screen.
- **Variant agnosticism:** Same result screen for Flip Card win and Scratch Card win — no visual difference in the result screen itself.
- **"Use Now" as primary CTA:** "Use Now" is visually more prominent than "Claim Coupon" on the win screen.
- **Locale — win (ja):** Win result in Japanese — both CTA labels, win message, all strings from `game.json`.
- **Locale — win (en):** Same screen in English.
- **Locale — lose (ja/en):** Same coverage for lose screen.
- **No replay on lose:** Lose screen has no replay button and no path to restart the session.
- **Touch targets:** All CTAs (both win and lose screens) meet 44px minimum touch target height.

## 9. Out of Scope

- Coupon issuance and AppLink navigation — owned by [E3](../reward-coupon/_epic-E3-reward-coupon.md).
- Communicating remaining play opportunities (e.g., "come back tomorrow") — owned by [E4](../game-session/_epic-E4-game-session.md).
- Game-variant-specific result visuals (e.g., the wheel segment displayed post-spin) — those are part of the variant's own animation, not the shared result screen.
- Social sharing of the result.
- Push notification after a win (native app concern).
