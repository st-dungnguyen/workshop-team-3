# Feature PRD: F2.3 — Game Result Screen

## 1. Feature Name

**Game Result Screen** — A shared win/lose result screen displayed after the game animation completes, presenting the outcome to the player and directing them to the appropriate next action.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

After the game variant finishes its reveal animation (F2.2), the result screen takes over to clearly communicate the outcome. This screen is shared across all game variants — Scratch Card, Flip Card, and any future variants all use the same result screen. The win screen is persistent: the player stays on it and actively chooses how to access their coupon. The lose path gives the player a warm, clear next step.

The result screen is the emotional peak of the player's experience: a win should feel rewarding and celebratory; a lose should be warm and encouraging — not punishing.

**Intended Audience:** Engineering team.

**Assumptions:**
- The result screen receives the outcome (`win` or `lose`) and the `couponInfo` (when outcome is `win`) from the game shell (F2.2) after the animation completes.
- The background coupon claim (F3.1) fires automatically before this screen appears — the result screen has no responsibility for triggering or monitoring the claim.
- On a win, the `couponId` is already available in memory (from the `play()` response). The result screen uses it directly for AppLink construction (F3.2).
- On a lose, there is no retry within the same session. Play limits are enforced by E4.
- All result screen text must be in both `ja` and `en` (`game.json` namespace).
- The result screen is the same regardless of which game variant was played.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Has just seen their outcome revealed; now needs to understand what they won (or didn't), and what to do next |

## 5. User Stories

- As a **PLAYER who won**, I want to see a clear confirmation of my win and a preview of my coupon so that I know exactly what I earned.
- As a **PLAYER who won**, I want two clear paths to access my coupon so that I can either use it right away or find it later in my coupon list.
- As a **PLAYER who lost**, I want a friendly, encouraging message so that I don't feel discouraged from coming back to the app in the future.
- As a **PLAYER**, I want the result screen to feel thematically consistent with the game so that the experience doesn't feel disjointed.

## 6. Requirements

### Functional Requirements

**Win state**

- **REQ-231**: When the session outcome is `win`, the system shall display the win result screen with a visually prominent win indicator (e.g., celebratory illustration, positive message) and a visual preview of the coupon reward (title, discount value, expiry date).
- **REQ-232**: The win result screen shall display two CTAs:
  - **"Use Coupon"** (`result.useCoupon`) — primary CTA; navigates the player to the specific won coupon detail screen in the native app via AppLink.
  - **"My Coupon"** (`result.myCoupon`) — secondary CTA; navigates the player to the native app's coupon list screen via AppLink.
  Both CTAs navigate directly — they do not trigger any API call. The coupon issuance is handled by the background claim (F3.1) which fires automatically before this screen appears.
- **REQ-233**: The win result screen shall remain visible after it appears. There shall be no auto-redirect to any external URL. The player must actively tap a CTA to leave the screen.
- **REQ-234**: The win result screen shall display the coupon preview (title, discount, expiry) using the data from the `play()` response. It shall not fetch coupon data from any additional API.

**Lose state**

- **REQ-241**: When the session outcome is `lose`, the system shall display the lose result screen with a warm, friendly message — the tone must be encouraging, not punishing.
- **REQ-242**: The lose result screen shall display a CTA to close the WebView and return to the native app.
- **REQ-243**: The lose result screen shall not offer a replay option within the same session. Whether the player can play again (next day, next window) is communicated by E4.

**Shared behavior**

- **REQ-251**: The result screen shall appear immediately after the variant signals animation completion — there shall be no blank or loading state between the animation end and the result screen appearing.
- **REQ-252**: All player-facing strings on the result screen must be available in `ja` and `en` via the `game.json` i18n namespace.
- **REQ-253**: The result screen layout and visual style shall be consistent with the warm Japanese food-brand aesthetic and the active game variant's visual theme.

### Constraints

- **CON-231**: The result screen is shared across all game variants. It must not contain variant-specific logic or visual elements (those belong to the variant itself, not the result screen).
- **CON-232**: Neither win CTA ("Use Coupon" or "My Coupon") shall trigger an API call. Navigation is direct via `window.location.href`. The background claim (F3.1) is not initiated from the result screen.
- **CON-233**: The win screen must not auto-navigate. The player's tap is the required trigger for leaving the win result screen.

### Guidelines

- **GUD-231**: The win state should use celebratory visual elements appropriate to the Japanese aesthetic (e.g., confetti, decorative motifs, warm gold tones) without being excessive.
- **GUD-232**: The lose state message should align with the seasonal campaign tone — for example, "また明日チャレンジしよう！" (Try again tomorrow!) rather than a generic "You lost."
- **GUD-233**: "Use Coupon" should be the visually primary CTA (filled/prominent, `btn-primary`) and "My Coupon" the secondary CTA (outlined/subdued, `btn-secondary`) — the business goal is to convert the coupon to an order, not just to save it.
- **GUD-234**: All CTAs (both win and lose screens) must have a minimum touch target of 44px height.

## 7. Acceptance Criteria

**Win path**

- **AC-231**: Given the game outcome is `win` and the animation has completed, when the result screen appears, then a win confirmation message, a coupon preview, a "Use Coupon" CTA, and a "My Coupon" CTA are all visible.
- **AC-232**: Given the win result screen is shown, when the player taps "Use Coupon", then the native app's coupon detail screen opens via AppLink to `/app/coupon/segment?id={couponId}` — no API call is sent.
- **AC-233**: Given the win result screen is shown, when the player taps "My Coupon", then the native app's coupon list opens via AppLink to `/app/coupon` — no API call is sent.
- **AC-234**: Given the win result screen has appeared, then no auto-redirect occurs — the screen remains until the player taps a CTA.
- **AC-235**: Given the background claim (F3.1) is still in flight when the win screen appears, then both CTAs are enabled and fully functional — the claim's in-flight state does not affect the CTAs.

**Lose path**

- **AC-241**: Given the game outcome is `lose` and the animation has completed, when the result screen appears, then a friendly lose message and a "Return to App" CTA are visible — no replay button is shown.
- **AC-242**: Given the lose result screen is shown, when the player taps the close CTA, then the WebView navigates to `{webViewHost}/close`.

**Shared behavior**

- **AC-251**: Given the animation completes (either variant), when the result screen appears, then no blank or loading state is observed between animation end and result display.
- **AC-252**: Given the result screen is displayed, when the locale is `ja`, then all text is in Japanese; when the locale is `en`, then all text is in English.
- **AC-253**: Given the active variant is Flip Card vs. Scratch Card, when both produce a `win` outcome, then the same result screen layout is shown in both cases.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Win flow — "Use Coupon":** Animation completes with `win` → result screen shows coupon preview + two CTAs → player taps "Use Coupon" → AppLink to `/app/coupon/segment?id={couponId}` — no API call in network tab.
- **Win flow — "My Coupon":** Same setup → player taps "My Coupon" → AppLink to `/app/coupon` — no API call in network tab.
- **No auto-redirect:** Win screen appears → player waits 10s → screen remains, no navigation fires.
- **CTAs enabled immediately:** Win screen appears while background claim is in flight → both CTAs tappable immediately.
- **Lose flow — full:** Animation completes with `lose` → result screen appears immediately → friendly message shown → player taps close → WebView closes.
- **Transition timing:** No gap or blank state between animation end and result screen.
- **Variant agnosticism:** Same result screen for Flip Card win and Scratch Card win — no visual difference in the result screen itself.
- **"Use Coupon" as primary CTA:** "Use Coupon" is visually more prominent than "My Coupon" on the win screen.
- **Locale — win (ja):** Win result in Japanese — both CTA labels, win message, coupon preview strings.
- **Locale — win (en):** Same screen in English.
- **Locale — lose (ja/en):** Same coverage for lose screen.
- **No replay on lose:** Lose screen has no replay button and no path to restart the session.
- **Touch targets:** All CTAs (both win and lose screens) meet 44px minimum touch target height.

## 9. Out of Scope

- Background coupon claim (firing the API call) — owned by [F3.1](../reward-coupon/f3.1-win-recording-and-coupon-issuance.md).
- AppLink URL construction and navigation logic — owned by [F3.2](../reward-coupon/f3.2-coupon-delivery-via-applink.md).
- Communicating remaining play opportunities (e.g., "come back tomorrow") — owned by [E4](../game-session/_epic-E4-game-session.md).
- Game-variant-specific result visuals (e.g., the card reveal displayed post-flip) — those are part of the variant's own animation, not the shared result screen.
- Social sharing of the result.
- Push notification after a win (native app concern).
- A "View Coupon List" tertiary CTA — the "My Coupon" CTA covers this use case.
