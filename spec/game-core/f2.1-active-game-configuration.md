# Feature PRD: F2.1 — Active Game Configuration

## 1. Feature Name

**Active Game Configuration** — Enables the team to configure multiple active game variants within a single campaign. When a player opens the WebView, the system randomly selects one of the campaign's active game variants to present, creating variety without requiring a frontend redeploy.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

The business requirement is to swap and manage mini games between seasons without updating the native app or redeploying the frontend. This feature defines how active game variants are determined and delivered to the WebView at runtime.

**Key design decisions:**

- Configuration lives in the backend, not in the frontend build artifact.
- **A single campaign remains the primary entity** — it owns the coupon pool, win probability, and all shared configuration.
- **A campaign may have multiple game variants active simultaneously.** When more than one variant is active, the backend randomly selects one for each WebView load. This introduces game variety — a player may see a different game on each visit.
- The frontend always receives a single variant per request — it is unaware of how many variants are active within the campaign.
- A redeploy is only required when adding a *new* variant module that does not yet exist in the frontend.

**Intended Audience:** Engineering team.

**Assumptions:**
- At any given time, exactly one campaign is marked active in the backend. The campaign owns the coupon pool (`campaign_coupons`) and `win_probability` — these are shared across all game variants within the campaign.
- A campaign may have one or more game variants marked as active. The backend selects one at random per request.
- The frontend fetches the configuration via an authenticated API endpoint on every WebView load — it does not cache the result across sessions.
- Currently supported variants: `scratch-card` and `flip-card`. Adding a new variant still requires a frontend code change to register the variant module.
- Configuration and eligibility checks both begin immediately after authentication (E1) completes — they run in parallel, and the player sees a single loading state until both resolve.
- If the active campaign has no active game variants, the system treats this as a configuration error (not a player-facing play limit).

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Unaware of the configuration — simply sees a game when opening the WebView. May see a different game variant on different visits when multiple variants are active |
| **HOST** | Does not interact with the config directly; opens the WebView URL, which always reflects a randomly selected active game variant |
| **SYSTEM** | Stores the campaign and its active game variants server-side; selects one active variant at random per request and returns it to the frontend |

> Note: This feature has no direct player-facing behavior beyond determining which game the player sees. It is listed as P0 because the entire variant system depends on it.

## 5. User Stories

- As a **business operator**, I want to activate multiple game variants within a single campaign so that players experience variety on each visit while sharing the same coupon pool and win probability.
- As a **business operator**, I want to activate or deactivate individual game variants independently so that I can manage the game lineup without affecting the campaign's coupon pool or win rate.
- As a **business operator**, I want to switch the active game variants by updating server records so that I can change the seasonal game lineup without a frontend deployment.
- As a **PLAYER**, I want the game to load automatically so that I always see a game without any action on my part — potentially a different one each time I visit.
- As a **developer**, I want the frontend to request the active variant at runtime so that a config change on the backend is immediately reflected on the next WebView open.

## 6. Requirements

### Functional Requirements

**Configuration fetch**

- **REQ-201**: Upon successful authentication (E1), the system shall immediately request the active game configuration from the backend. This request shall be made on every WebView load — the result must not be cached across sessions.
- **REQ-202**: The configuration response shall include at minimum: the active campaign identifier and the selected game variant identifier. The frontend always receives a single variant per request.
- **REQ-203**: While the configuration request is in flight, the system shall display a loading indicator. The game board must not be rendered or accessible during this time.
- **REQ-204**: The configuration fetch and the session eligibility check (E4) shall run in parallel after authentication completes. The player shall see a single loading state while both are in flight; the game board shall only appear when both have resolved successfully.

**Multi-variant random selection (backend)**

- **REQ-211**: A campaign shall support one or more game variants. Each variant within a campaign may be independently marked as active or inactive.
- **REQ-212**: When the active campaign has multiple active game variants, the backend shall randomly select one variant per configuration request. The selection shall be uniformly random across all active variants.
- **REQ-213**: When the active campaign has exactly one active game variant, the backend shall return that variant (no randomization needed).
- **REQ-214**: When no campaign is active, or the active campaign has no active game variants, the backend shall return a 404 response with code `NO_ACTIVE_CAMPAIGN`.
- **REQ-215**: All active game variants within a campaign shall share the campaign's `win_probability` and coupon pool (`campaign_coupons`). There is no per-variant win rate or coupon pool.

**Variant rendering**

- **REQ-205**: The system shall render only the game variant declared in the configuration response. No other variant shall be rendered or loaded.
- **REQ-206**: The system shall support switching between `scratch-card` and `flip-card` variants via backend config changes alone, with no frontend change or redeploy required.
- **REQ-207**: The variant module (animation, interaction) shall be decoupled from the configuration fetch. The game shell passes the resolved variant identifier to the variant renderer; the renderer does not read configuration directly.

**Error handling**

- **REQ-208**: When the configuration request fails (network error, 500, 503) or returns no active configuration (404), the system shall display a `game.sessionCheckError` screen with a retry button. The game board must not be shown.
- **REQ-209**: When the player taps retry on the error screen, the system shall re-request the configuration. If multiple variants are active, the backend may return a different variant than the previous attempt (a new random selection occurs).
- **REQ-210**: When the backend returns 401 during the configuration request, the system shall display the `auth.unauthorized` error screen — the player's token has expired.

### Security Requirements

- **SEC-201**: The configuration request shall include the player's validated auth token so the backend can confirm the request is from an authenticated player.
- **SEC-202**: The configuration response must not contain secrets (API keys, service tokens). It is delivered to the WebView and must be treated as client-visible data.
- **SEC-203**: The configuration response must not reveal how many game variants are active or which other variants exist — only the selected variant is returned.

### Validation Rules

- **VAL-201**: The frontend shall reject a configuration response that declares an unrecognized variant identifier and display a `game.sessionCheckError` screen. It must not silently render nothing or crash with an unhandled error.

### Constraints

- **CON-201**: Exactly one campaign is active at any given time. Multiple game variants may be active within that campaign. The backend selects one variant at random per request. The frontend always renders exactly one variant per WebView load.
- **CON-202**: Introducing a *new* variant module that has never existed in the frontend still requires a frontend code change to register the variant. Config changes alone can only switch between already-registered variants.
- **CON-203**: The configuration result must not be persisted to `localStorage` or any client-side store. It is fetched fresh on every WebView load.
- **CON-204**: The random selection is per-request, not per-player. The same player may receive different variants on consecutive WebView opens. There is no affinity or stickiness.
- **CON-205**: All active variants within a campaign share the same `win_probability` and `campaign_coupons`. Per-variant win rates or coupon pools are not supported.

### Guidelines

- **GUD-201**: The loading state for configuration fetch should be visually identical to the eligibility loading state — the player experiences one smooth loading sequence, not two sequential spinners.
- **GUD-202**: Variant identifiers should be stable, lowercase hyphenated strings (e.g., `scratch-card`, `flip-card`) that match the variant module names — this makes the mapping self-documenting.
- **GUD-203**: When adding weighted random selection in the future (e.g., 70% scratch-card, 30% flip-card), a `selection_weight` column on the campaign-variant relationship would support this. This is not required for the initial implementation (uniform random is sufficient).

## 7. Acceptance Criteria

- **AC-201**: Given authentication is complete, when the WebView loads, then a configuration request is sent to the backend before the game board is rendered.
- **AC-202**: Given the backend returns `{ gameVariant: "scratch-card", campaignId: "..." }`, then the Scratch Card game is rendered and no Flip Card UI appears.
- **AC-203**: Given the backend returns `{ gameVariant: "flip-card", campaignId: "..." }`, then the Flip Card game is rendered and no Scratch Card UI appears.
- **AC-204**: Given a backend operator changes the active variants from `scratch-card` only to `flip-card` only (no frontend change), when a player next opens the WebView, then the Flip Card game is shown.
- **AC-205**: Given the configuration request fails (500 or network error), then a `game.sessionCheckError` screen with retry is shown — the game board is not rendered.
- **AC-206**: Given the retry button is tapped and the backend returns a valid config, then the game board appears.
- **AC-207**: Given the configuration request returns an unrecognized variant identifier, then the `game.sessionCheckError` screen is shown and the system does not crash.
- **AC-208**: Given authentication completes, then the configuration request and the eligibility check (E4) both begin in parallel — neither waits for the other to complete.
- **AC-209**: Given the backend returns 401 during config fetch, then `auth.unauthorized` is shown (not `game.sessionCheckError`).
- **AC-210**: Given a campaign has both `scratch-card` and `flip-card` active, when a player opens the WebView multiple times, then sometimes Scratch Card is shown and sometimes Flip Card is shown (random selection).
- **AC-211**: Given a campaign has two active variants, when the backend receives a config request, then it returns exactly one variant — not a list.
- **AC-212**: Given a campaign has `scratch-card` and `flip-card` active, when the operator deactivates `scratch-card`, then only `flip-card` is returned on subsequent requests.
- **AC-213**: Given the active campaign has no active game variants, when a player opens the WebView, then a 404 / `game.sessionCheckError` screen is shown.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path (single active variant):** Auth completes -> config + eligibility both requested in parallel -> backend returns the sole active variant -> spinner resolves -> correct game board shown.
- **Happy path (multiple active variants):** Campaign has scratch-card + flip-card active -> repeated config requests return both variants over time (statistical verification).
- **Config swap (no redeploy):** Backend updated to different active variant set -> next WebView open reflects new selection pool with no frontend change.
- **Deactivate one variant:** Campaign has two active variants -> deactivate one -> subsequent requests never return the deactivated variant.
- **Activate additional variant:** Campaign has one active variant -> activate a second -> subsequent requests may return either variant.
- **Shared win probability:** Two active variants in same campaign -> both use the campaign's `win_probability` -> no per-variant override possible.
- **Shared coupon pool:** Two active variants in same campaign -> winning on either variant draws from the same `campaign_coupons` pool.
- **Config request 500:** Backend returns 500 -> `game.sessionCheckError` shown, game board absent.
- **Config request 503:** Backend returns 503 -> same as 500 handling.
- **Config request 401:** Backend returns 401 -> `auth.unauthorized` shown.
- **No active variants (404):** All variants deactivated in the active campaign -> `game.sessionCheckError` shown.
- **No active campaign (404):** No campaign with `is_active = true` -> `game.sessionCheckError` shown.
- **Retry flow:** Error screen shown -> player taps retry -> config re-requested (new random selection) -> board shown on success.
- **Unrecognized variant:** Backend returns variant key not registered in frontend -> `game.sessionCheckError` shown, no crash.
- **Parallel loading:** Config and eligibility both in-flight simultaneously — single spinner, no sequential delay.
- **Config not cached:** Player opens WebView -> plays -> closes -> reopens -> fresh config request made (not served from cache). May receive a different variant.
- **Token 401 during config:** Token expired between auth and config fetch -> `auth.unauthorized` shown.
- **No information leakage:** Config response contains only the selected variant — no count or list of other active variants.

## 9. Out of Scope

- Runtime variant switching while the WebView is open (mid-session) — config is fetched once per WebView load.
- Weighted random selection (e.g., 70% scratch-card, 30% flip-card) — initial implementation uses uniform random. See GUD-203 for future path.
- Player-sticky variant assignment (e.g., always show the same variant to the same player) — selection is per-request, not per-player.
- Per-variant win probability or coupon pool — all variants share the campaign's settings.
- Multiple active campaigns — exactly one campaign is active at a time.
- An admin UI for managing campaign configuration — operators update the backend directly (API or DB).
- Adding a new variant module to the frontend — that requires a code change; this feature only covers switching between already-registered variants.
- Campaign coupon pool management — covered by [F2.6 — Campaign & Coupon Management](./f2.6-campaign-coupon-management.md).
- Session play-limit rules — owned by [E4](../game-session/_epic-E4-game-session.md).
- A/B testing with analytics tracking — this is random selection, not a measured experiment.
