# Feature PRD: F2.1 — Active Game Configuration

## 1. Feature Name

**Active Game Configuration** — Enables the team to declare which game variant is active per deploy through a single configuration entry, so that swapping seasonal games requires no architectural changes.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

The business requirement is to swap mini games between seasons without updating the native app. This feature defines the configuration mechanism that makes that possible. The active game variant is declared in a deploy-time configuration file. When the season changes, only this configuration and the new variant module need to change — the shell, auth, session, and reward layers are untouched.

**Intended Audience:** Engineering team.

**Assumptions:**
- At any given time, exactly one game variant is active. There is no multi-variant or A/B scenario.
- The configuration is set at build/deploy time. There is no runtime switching or CMS-driven config.
- Currently supported variants: `scratch-card` (cào trúng thưởng) and `flip-card` (lật thẻ).
- Future variants can be added by implementing the variant contract (F2.2) and registering in this configuration — no shell changes required.
- Campaign-level metadata (coupon ID, validity window, session limits) is part of this config and consumed by E3 and E4 respectively.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Unaware of the configuration — simply sees the active game when opening the WebView |
| **HOST** | Does not interact with the config directly; opens the WebView URL which already reflects the active game |

> Note: This feature has no direct player-facing behavior. Its consumers are the engineering team and the game shell. It is listed as P0 because the entire variant system depends on it.

## 5. User Stories

- As a **developer**, I want to declare the active game variant in a single location so that switching seasonal games requires only changing that entry and redeploying.
- As a **developer**, I want the configuration to include campaign metadata so that the same deploy also sets the correct coupon and session parameters for the new season.

## 6. Requirements

### Functional Requirements

- **REQ-201**: The system shall read the active game variant from the deploy-time configuration on startup.
- **REQ-202**: The system shall render only the game variant declared in the active configuration. No other variant shall be rendered or loaded.
- **REQ-203**: The configuration shall include at minimum: the active variant identifier, the campaign identifier, and any parameters required by E3 (coupon settings) and E4 (session limit settings).
- **REQ-204**: The system shall fail with a clear error at startup if the declared active variant is not a recognized, implemented variant — it must not silently render nothing or crash with an opaque error.

### Constraints

- **CON-201**: The active variant is fixed at deploy time. There is no mechanism to switch variants while the WebView is running.
- **CON-202**: The configuration must not contain secrets (API keys, tokens). It is a client-side artifact and must be treated as publicly visible.

### Guidelines

- **GUD-201**: The configuration should be a single, clearly named file at a predictable location so that any team member can find and update it without deep codebase knowledge.
- **GUD-202**: Each variant identifier should be a stable string key (e.g., `"lucky-wheel"`, `"scratch-card"`) that matches the variant's module name — this makes the mapping self-documenting.

## 7. Acceptance Criteria

- **AC-201**: Given the configuration declares `activeVariant: "scratch-card"`, when the WebView loads, then the Scratch Card game is rendered and no Flip Card UI appears.
- **AC-202**: Given the configuration declares `activeVariant: "flip-card"`, when the WebView loads, then the Flip Card game is rendered and no Scratch Card UI appears.
- **AC-203**: Given the configuration declares an unrecognized variant (e.g., `activeVariant: "unknown-game"`), when the WebView loads, then the system displays a clear error message and does not render a broken game UI.
- **AC-204**: Given a developer changes `activeVariant` from `"scratch-card"` to `"flip-card"` and redeploys, when the WebView next loads, then the Flip Card game is shown — with no changes required to the native app.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Scratch Card active:** Config set to `scratch-card` → only Scratch Card renders, no Flip Card UI.
- **Flip Card active:** Config set to `flip-card` → only Flip Card renders, no Scratch Card UI.
- **Game swap:** Change config, redeploy → correct variant loads, old variant absent.
- **Unknown variant:** Config declares unrecognized key → error state shown, no crash.
- **Campaign metadata passed:** E3 and E4 correctly receive coupon and session-limit params from config.

## 9. Out of Scope

- Runtime variant switching without a redeploy.
- CMS-driven or API-driven variant selection.
- A/B testing or multi-variant experiments.
- The implementation details of individual game variant modules — those are covered in F2.2.
