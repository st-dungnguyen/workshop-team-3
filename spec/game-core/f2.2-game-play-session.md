# Feature PRD: F2.2 — Game Play Session

## 1. Feature Name

**Game Play Session** — Defines the shared session lifecycle and the variant contract that allows Lucky Wheel and Scratch Card (and future variants) to plug into the game shell with identical underlying mechanics.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

All game variants share the same play session flow: the player initiates play, the backend determines the outcome server-side, the variant plays its reveal animation, and the result is delivered to the result screen. This feature specifies that shared lifecycle and the contract each variant must fulfill — ensuring that swapping variants never requires changes to session management, outcome handling, or the reward handoff.

**Intended Audience:** Engineering team.

**Assumptions:**
- Win/lose is determined by the backend before the animation plays. The frontend never generates or modifies the outcome.
- The play initiation is a single action (one tap). There is no multi-step or multi-round mechanic.
- Session eligibility (play limit enforcement) is checked before the session enters the `initiated` state — this is governed by [E4](../game-session/_epic-E4-game-session.md). This feature assumes eligibility has already been confirmed.
- Both Lucky Wheel and Scratch Card receive the same outcome payload from the backend and differ only in how they animate the reveal.
- The session is single-attempt: once initiated, the outcome cannot be changed and the session cannot be replayed.

### Current Variants

| Variant | Player Interaction | Animation Style |
|---|---|---|
| Scratch Card (cào trúng thưởng) | Scratch gesture over the card surface | Scratch layer progressively reveals the win/lose symbol beneath; auto-completes at 50–70% threshold |
| Flip Card (lật thẻ) | Tap one card from a set of face-down cards | Selected card flips with animation to reveal the outcome; remaining cards dim or briefly animate to signal round end |

Both variants receive `{ outcome: "win" | "lose" }` from the shell and animate accordingly. The shell does not know or care which animation is playing.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Sees the game board, performs the interaction (tap or scratch), watches the animation, and discovers their result |
| **SYSTEM** | Receives the play initiation request from the frontend, determines the outcome, and returns it to the frontend |

## 5. User Stories

- As a **PLAYER**, I want to tap (or scratch) to play the game so that I can discover my result through an engaging animation.
- As a **PLAYER**, I want the game to feel responsive and fair so that I trust the outcome was determined impartially.
- As a **SYSTEM**, I want to be the sole authority on game outcomes so that results cannot be manipulated by the client.
- As a **developer**, I want each game variant to implement the same contract so that adding a new seasonal game requires only building the variant, not modifying shared session logic.

## 6. Requirements

### Functional Requirements

**Session Lifecycle**

- **REQ-211**: The game session shall progress through the following states in order: `pending → initiated → resolving → revealing → completed`. No state may be skipped.
- **REQ-212**: The system shall display the game board in the `pending` state, ready for player interaction.
- **REQ-213**: When the player performs the play action (tap to spin or scratch gesture), the session shall transition to `initiated` and the system shall submit a play request to the backend.
- **REQ-214**: While awaiting the backend response (`resolving` state), the system shall prevent the player from initiating a second play action.
- **REQ-215**: When the backend returns the outcome, the session shall transition to `revealing` and the active variant shall begin its reveal animation.
- **REQ-216**: When the reveal animation completes, the session shall transition to `completed` and the result screen (F2.3) shall be shown.
- **REQ-217**: If the backend returns an error (500, 503) during outcome resolution, the system shall display a `game.serverError` error state with a retry option — without counting the failed attempt as a played session.
- **REQ-218**: If the backend returns a session-ineligible response (player has already played today), the system shall display the `game.alreadyPlayed` state and not allow play initiation.

**Variant Contract**

- **REQ-221**: Each game variant shall accept an outcome value (`win` or `lose`) from the shell and animate accordingly.
- **REQ-222**: Each game variant shall signal to the shell when its reveal animation has completed, so the shell can transition to the `completed` state and show the result screen.
- **REQ-223**: Each game variant shall not contain session management, outcome determination, or coupon logic — those belong to the shell and E3 respectively.
- **REQ-224**: Each game variant shall be renderable in a defined layout area provided by the shell. The variant must not control the full screen layout.

**Scratch Card specific**

- **REQ-231**: The Scratch Card variant shall display a single card with a scratchable surface layer. The player shall reveal the result by performing a scratch gesture over the card.
- **REQ-232**: The system shall consider the scratch "complete" when 50–70% of the card surface has been scratched, at which point the system shall automatically fully reveal the outcome and signal completion to the shell — the player does not need to scratch the entire surface.
- **REQ-233**: The scratch surface shall clearly indicate to the player where and how to scratch (e.g., visual texture, instructional label above the scratch area).

**Flip Card specific**

- **REQ-241**: The Flip Card variant shall display a set of face-down cards. The exact number of cards is defined by the implementation but must be more than one to create meaningful choice.
- **REQ-242**: The player shall initiate play by tapping one card from the set. Only one card may be selected per session.
- **REQ-243**: Once the player taps a card, the selected card shall flip with an animation to reveal the backend-determined outcome. The flip animation must accurately reflect the `win` or `lose` outcome — it must not be random or misleading.
- **REQ-244**: After the selected card reveals the outcome, the remaining unselected cards shall visually signal that the round is over — for example, by dimming or performing a subtle reverse-flip animation. The unselected cards must not reveal alternative outcomes.
- **REQ-245**: Once a card has been selected, the other cards must be non-interactive for the remainder of the session.

### Security Requirements

- **SEC-211**: The outcome (`win` or `lose`) shall only be received from the backend. The frontend shall not compute, predict, or override the outcome at any point.
- **SEC-212**: The play request sent to the backend shall include the player's validated token so the backend can associate the outcome with the correct player identity.

### Validation Rules

- **VAL-211**: The play action shall only be available when the session is in `pending` state. Tapping spin or scratching in any other state shall have no effect.

### Constraints

- **CON-211**: Each game session is single-attempt. Once the session has transitioned to `initiated`, the player cannot restart or cancel the current attempt.
- **CON-212**: The reveal animation must accurately reflect the backend-determined outcome. It is not acceptable to play a random animation and then show a different result.

### Guidelines

- **GUD-211**: The reveal animation should feel satisfying and suspenseful — enough time to build excitement (approximately 3–5 seconds) without frustrating the player with excessive wait time.
- **GUD-212**: The game board and animations should be consistent with the warm Japanese food-brand aesthetic (rounded shapes, warm colors, friendly illustrations).
- **GUD-213**: All instructional text (how to spin, how to scratch) must be available in both `ja` and `en` via the `game.json` i18n namespace.

## 7. Acceptance Criteria

**Session lifecycle**

- **AC-211**: Given the player is on the game board (`pending`), when they perform the play action, then the session moves to `initiated` and the play action becomes unavailable.
- **AC-212**: Given the session is in `resolving`, when the backend returns `{ outcome: "win" }`, then the active variant begins its win animation.
- **AC-213**: Given the session is in `resolving`, when the backend returns `{ outcome: "lose" }`, then the active variant begins its lose animation.
- **AC-214**: Given the backend returns a 500 error during `resolving`, then the system shows a `game.serverError` screen with a retry button, and the session remains retryable (not counted as played).
- **AC-215**: Given the reveal animation completes, then the session moves to `completed` and the result screen (F2.3) appears.

**Scratch Card**

- **AC-231**: Given the active variant is Scratch Card, when the player scratches enough of the surface (50–70% threshold), then the outcome is automatically fully revealed and the shell receives the completion signal.
- **AC-232**: Given the scratch is in progress and below the completion threshold, then the result screen does not appear and the outcome is not yet fully revealed.
- **AC-233**: Given the scratch threshold is reached, then the system auto-completes the reveal — the player does not need to scratch the remaining surface.

**Flip Card**

- **AC-241**: Given the active variant is Flip Card and the player taps one card, then that card flips with animation to reveal the correct backend-determined outcome.
- **AC-242**: Given a card has been tapped and is flipping, then the remaining cards become non-interactive and begin their end-of-round visual treatment (dim or subtle animation).
- **AC-243**: Given the flip animation completes, then the shell receives the completion signal and the result screen is shown.
- **AC-244**: Given a card is selected and flipping, when the player taps another card, then no action is taken.

**Variant contract**

- **AC-251**: Given the config is changed from `scratch-card` to `flip-card` and redeployed, then the Flip Card game plays identically to Scratch Card in terms of session lifecycle — same states, same outcome flow, same result screen.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path (win — Scratch Card):** Player scratches to 50–70% threshold → system auto-reveals → `resolving` → backend returns `win` → result screen shows win state.
- **Happy path (lose — Scratch Card):** Same flow, backend returns `lose` → result screen shows lose state.
- **Happy path (win — Flip Card):** Player taps a card → `resolving` → backend returns `win` → selected card flips to reveal win → other cards dim → result screen shows win state.
- **Happy path (lose — Flip Card):** Same flow, backend returns `lose` → selected card reveals lose → result screen shows lose state.
- **Server error during resolving:** Backend returns 500 → `game.serverError` shown with retry; session not consumed.
- **Server error retry:** Error shown → player taps retry → backend returns `win` → normal win flow.
- **Scratch — auto-complete at threshold:** Player scratches 55% of surface → system completes reveal automatically without player scratching further.
- **Flip Card — multi-tap prevention:** Player taps two cards quickly → only the first tap is registered; second card remains face-down.
- **Session ineligible:** Backend signals player has already played → `game.alreadyPlayed` state shown, interaction disabled.
- **Animation integrity:** Outcome received is `win` → animation shows win (not lose) and vice versa — cannot be overridden client-side.
- **Variant swap:** Config changed to other variant, redeployed → identical session lifecycle, different animation only.
- **Locale:** All game UI strings display in `ja` by default; switching to `en` updates all strings correctly.
- **App backgrounded mid-animation:** Player backgrounds the native app while animation plays → on resume, animation state is handled gracefully (no crash, no double-counting).

## 9. Out of Scope

- Determining session eligibility (play limit per day/window) — owned by [E4](../game-session/_epic-E4-game-session.md).
- The reward/coupon flow after a win — owned by [E3](../reward-coupon/_epic-E3-reward-coupon.md).
- Adding a third game variant — the contract defined here enables it, but the implementation is a future task.
- Game analytics, play history display, or leaderboards.
- Sound effects or haptic feedback (outside current scope; may be added per variant).
- Accessibility support beyond basic touch targets (future enhancement).
