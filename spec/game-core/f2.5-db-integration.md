# Feature PRD: F2.5 — Persistent Game Session Storage (PostgreSQL)

## 1. Feature Name

**Persistent Game Session Storage** — Replaces the in-memory play-tracking store with a PostgreSQL database so that game session records survive server restarts and are accessible across multiple API instances.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

The current backend stores every `GameSession` record in a Node.js in-memory `Map`. This means all play history is lost whenever the server process restarts or is redeployed — breaking eligibility checks for players who played earlier in the same day. It also prevents horizontal scaling (multiple API instances would not share state).

This feature replaces the in-memory store with a PostgreSQL database to make `GameSession` records durable, queryable, and shareable across instances. It covers the data model, the local development environment (Docker Compose), the schema migration strategy, and the updated service contracts.

**Intended Audience:** Engineering team (backend).

**Assumptions:**
- PostgreSQL is the chosen database engine for both local development and production.
- All daily play-limit queries are date-anchored to UTC midnight, matching the existing `todayKey()` convention.
- The `userId` value is the `sub` claim from the validated JWT — a stable, opaque string identifier.
- The migration approach is file-based SQL scripts run in order; no ORM migration framework is mandated.
- Docker Compose is used exclusively for local development. Production environment database provisioning is out of scope.
- A single `game_sessions` table satisfies all current query requirements. Additional tables may be introduced in future features without altering this spec.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Unaware of the storage change — experiences only the consequence: eligibility checks remain accurate even after a server restart |
| **SYSTEM (game-api)** | Records every game session outcome, checks eligibility, and calculates next-play time — now against a durable DB rather than an in-memory Map |
| **Developer** | Runs `docker compose up` locally to start the database and interacts with it through the service layer |

## 5. User Stories

- As a **PLAYER**, I want my play record to be remembered even if the server restarts so that I cannot play more than once per day by timing a restart.
- As a **SYSTEM**, I want to query whether a player has played today in a single, indexed database query so that eligibility checks remain fast as player volume grows.
- As a **developer**, I want a one-command local database setup so that I can work on game-api without installing PostgreSQL globally or depending on a shared remote instance.

## 6. Requirements

### Functional Requirements

**Local Development Environment**

- **REQ-251**: The project shall include a `docker-compose.yml` that starts a PostgreSQL instance with all required credentials pre-configured via environment variables.
- **REQ-252**: The Docker Compose setup shall expose PostgreSQL on a configurable port (default `5432`) and mount a named volume so that data persists across container restarts.
- **REQ-253**: The `game-api` `.env.example` shall document the `DATABASE_URL` variable in `postgresql://user:password@host:port/dbname` connection string format.

**Database Schema**

- **REQ-254**: The system shall create a `game_sessions` table with the following fields:
  - `id` — auto-incrementing integer primary key
  - `user_id` — non-null string (the JWT `sub` claim); indexed for lookup performance
  - `play_date` — non-null UTC date (`YYYY-MM-DD`); used for daily uniqueness checks; indexed
  - `outcome` — non-null enum-like string constrained to `'win'` or `'lose'`
  - `coupon_id` — nullable string; populated only on win outcomes
  - `created_at` — non-null timestamp with time zone; set to the current time at insert; not mutable
- **REQ-255**: The combination of `(user_id, play_date)` shall not be unique at the DB constraint level — uniqueness is enforced at the application layer via the eligibility check before insert.

**Migration Strategy**

- **REQ-256**: The project shall include a `migrations/` directory in `game-api` containing ordered SQL files (e.g., `001_create_game_sessions.sql`).
- **REQ-257**: The system shall provide a `migrate` script (runnable via `pnpm run migrate`) that applies all pending migration files to the database in order, idempotently (already-applied migrations must not be re-run).
- **REQ-258**: Migrations shall be tracked by a `schema_migrations` table that records the filename of every applied migration. The migrate script shall read this table to determine which files are pending.

**Service Layer**

- **REQ-259**: The `draws` service shall implement the following operations against the database:
  - `hasPlayedToday(userId)` — returns `true` if a row exists in `game_sessions` where `user_id = $1` AND `play_date = current UTC date`; otherwise `false`
  - `getNextPlayAt(userId)` — returns an ISO 8601 timestamp representing UTC midnight of the following day when the player is ineligible; returns `null` when the player is eligible
  - `recordPlay(userId, { outcome, couponId })` — inserts a new row into `game_sessions` with the current UTC date, outcome, and optional `coupon_id`
- **REQ-260**: The database connection shall be managed as a Fastify plugin, registered before the routes, so that route handlers can access it via the decorated Fastify instance (e.g., `fastify.db`).
- **REQ-261**: On startup, if the database is unreachable, the API shall fail to start with a clear error message. It must not start and silently serve requests using a fallback in-memory store.

### Security Requirements

- **SEC-251**: Database credentials (`DATABASE_URL`) shall never be hardcoded in source files. They must be loaded exclusively from environment variables.
- **SEC-252**: The `game_sessions` table shall not expose raw DB rows to API responses. All external-facing data must pass through the service layer.

### Validation Rules

- **VAL-251**: `outcome` values inserted into `game_sessions` must be either `'win'` or `'lose'`. Any other value shall be rejected at the application layer before reaching the database.
- **VAL-252**: `user_id` must be a non-empty string. An empty or null `user_id` must never be inserted.

### Constraints

- **CON-251**: The in-memory `Map` in `draws.service.js` must be fully removed once the DB-backed implementation is in place. There must be no code path that falls back to the in-memory store at runtime.
- **CON-252**: The `game_sessions` table and migration scripts are append-only for existing data. Once a row is inserted, it is never updated or deleted by the game-api. Corrections are out-of-band operations.
- **CON-253**: The `docker-compose.yml` shall declare only the PostgreSQL service. No other services (Redis, application container, etc.) shall be added under this feature.

### Guidelines

- **GUD-251**: The `play_date` column should store a `DATE` type (not a timestamp) to make daily uniqueness queries explicit and index-friendly — no date-truncation functions needed at query time.
- **GUD-252**: All DB-bound parameters shall use parameterized queries. String interpolation in SQL is prohibited.
- **GUD-253**: The migrate script should log each migration file as it is applied, and print "No pending migrations" when already up to date.

## 7. Acceptance Criteria

- **AC-251**: Given `docker compose up -d` is run in the project root, then a PostgreSQL container starts, is healthy, and accepts connections on the configured port without any additional manual setup.
- **AC-252**: Given `pnpm run migrate` is executed against a fresh database, then the `schema_migrations` and `game_sessions` tables are created and the migration run is recorded.
- **AC-253**: Given `pnpm run migrate` is run a second time against the same database, then no error is thrown and no migration is re-applied.
- **AC-254**: Given a player plays a game (POST `/game/play`), then a row is inserted into `game_sessions` with the correct `user_id`, `play_date` (today UTC), `outcome`, and `coupon_id`.
- **AC-255**: Given the server is restarted after a player has played, when the eligibility check (GET `/game/eligibility`) is made for that player on the same UTC day, then the response is `{ eligible: false }`.
- **AC-256**: Given a player played yesterday (UTC) and it is now a new UTC day, when the eligibility check is made, then the response is `{ eligible: true }`.
- **AC-257**: Given `DATABASE_URL` is missing from the environment, when `game-api` starts, then it exits immediately with a descriptive error message — it does not start and serve requests.
- **AC-258**: Given an insert is attempted with an empty `user_id`, then the insert is rejected at the service layer before reaching the database.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path — first play of day:** Player with no record for today → `hasPlayedToday` returns `false` → play allowed → `recordPlay` inserts row → subsequent `hasPlayedToday` returns `true`.
- **Happy path — already played:** Player with a row for today's UTC date → `hasPlayedToday` returns `true` → play blocked → 403 returned.
- **Day boundary (UTC midnight):** Player played at 23:59 UTC → server clock advances to 00:00 UTC → eligibility check returns `eligible: true` (new day, new play).
- **Server restart persistence:** Row inserted → API process killed and restarted → row still present → eligibility check still returns ineligible.
- **Migration idempotency:** Run migrate twice on same DB → second run completes without error and without duplicate table creation.
- **Migration on fresh DB:** Empty database → run migrate → both `schema_migrations` and `game_sessions` created correctly with expected columns and indexes.
- **Missing DATABASE_URL:** Start API with no `DATABASE_URL` → process exits with non-zero code and error message in logs.
- **DB unreachable:** Start API with a `DATABASE_URL` pointing to an unavailable host → process fails to start (does not hang indefinitely).
- **Win record:** `recordPlay(userId, { outcome: 'win', couponId: 'C123' })` → row inserted with `outcome = 'win'` and `coupon_id = 'C123'`.
- **Lose record:** `recordPlay(userId, { outcome: 'lose' })` → row inserted with `outcome = 'lose'` and `coupon_id = NULL`.
- **SQL injection guard:** Service called with `user_id = "' OR '1'='1"` → parameterized query prevents injection; row is recorded or rejected as per validation, no unintended data is returned.

## 9. Out of Scope

- Production database provisioning, connection pooling configuration for high concurrency, or read replicas.
- Any ORM integration (e.g., Prisma, TypeORM, Drizzle) — raw SQL via the `pg` driver is sufficient for this feature.
- A database admin UI or migration rollback mechanism.
- Archiving or purging old `game_sessions` rows.
- Adding tables for users, campaigns, coupons, or rewards — only `game_sessions` is in scope.
- Changing any frontend (game-ui) behavior — this feature is entirely backend-scoped.
- Redis or any other secondary data store.
