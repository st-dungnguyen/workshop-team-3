# Feature PRD: F2.6 — Campaign & Coupon Management

## 1. Feature Name

**Campaign & Coupon Management** — Enables operators to define a campaign's coupon pool — multiple coupon options with weighted win probabilities — so that backend outcome resolution draws from a real, configurable prize set rather than a single hardcoded coupon.

## 2. Epic

- **Parent Epic:** [E2 — Game Core](./_epic-E2-game-core.md)
- **Priority:** P1 — High

## 3. Purpose & Scope

Previously, the game issued a single coupon whose ID, title, and discount were hardcoded in server environment variables. This meant every winner received the same reward and changing the coupon required a server redeploy.

This feature introduces a **campaign coupon pool**: a set of coupons associated with a campaign, each with a weight that governs how often it is selected as the winning prize. When a player wins, the backend draws a coupon from the active pool using weighted random selection and issues it. Operators can configure multiple prize tiers (e.g., a common 500円 coupon with weight 3, a rare 1,000円 coupon with weight 1) that change the prize distribution without any code deployment.

This feature also formalises the **campaign** as a first-class data entity, moving win probability out of environment variables and into the campaign record.

**Intended Audience:** Engineering team (backend).

**Assumptions:**
- A campaign has exactly one active coupon pool at a time. All coupons in the pool are associated to the same campaign.
- Coupon selection is weighted random: coupons with higher weight are more likely to be selected.
- A coupon is only eligible for selection if its validity window (`start_date` to `end_date`) includes the current server time at the moment of play.
- If the active campaign has no eligible coupons (all expired or none configured), the play is blocked and an error is returned — the system must not issue a win without a coupon to back it.
- Win probability (the chance of winning at all) is stored on the campaign, not on individual coupons. All coupons share the same chance of winning; weights only govern which coupon is awarded when a win occurs.
- The frontend receives no information about coupon weights or the pool structure — it only receives the selected coupon after a win.
- There is no player-facing coupon selection or preview of the prize pool beyond what the game variant's result screen displays.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Plays the game, wins (or loses), and receives whichever coupon was selected by the backend. Unaware of the pool structure or coupon weights. |
| **SYSTEM** | On a win, queries the active coupon pool for the campaign, selects a coupon via weighted random, and issues it via the Coupon API. |

> Note: This feature has no direct player-facing UI beyond the coupon detail shown on the result screen after a win (covered by [F2.3](./f2.3-game-result-screen.md) and [E3](../reward-coupon/_epic-E3-reward-coupon.md)).

## 5. User Stories

- As a **business operator**, I want to define multiple prize tiers for a campaign so that I can run promotions with a mix of coupon values (e.g., 80% chance of 500円, 20% chance of 1,000円 among winners).
- As a **business operator**, I want each coupon in the pool to have a validity window so that I can schedule seasonal coupons to activate and expire automatically without manual intervention.
- As a **SYSTEM**, I want to select a coupon at play-time using weighted random so that prize distribution matches the configured weights over a large number of plays.
- As a **developer**, I want the coupon pool to be seeded with realistic default data on first setup so that local development works without manual DB configuration.

## 6. Requirements

### Functional Requirements

**Campaign data model**

- **REQ-261**: A campaign record shall store: a unique identifier, a human-readable name, the active game variant identifier, a flag indicating whether the campaign is currently active, and a win probability (a decimal between 0 and 1 inclusive).
- **REQ-262**: Exactly one campaign shall be marked active at any given time. The system shall use the active campaign's win probability when resolving play outcomes.
- **REQ-263**: The win probability stored on the campaign shall replace all environment-variable-based win probability configuration. Once this feature is in place, no server environment variable shall govern win probability.

**Campaign coupon pool**

- **REQ-264**: A campaign coupon record shall store: the campaign it belongs to, the external coupon identifier (used when issuing via the Coupon API), a display title, a display discount value, a validity start date, a validity end date, and a positive integer weight.
- **REQ-265**: A campaign may have one or more coupons in its pool. The minimum is one coupon; there is no defined maximum.
- **REQ-266**: A coupon is eligible for selection only if both conditions are true at the time of play: (a) its `start_date` is on or before the current server time, and (b) its `end_date` is after the current server time.

**Weighted random selection**

- **REQ-267**: When a player wins, the system shall select one coupon from the active campaign's eligible pool using weighted random selection. A coupon with weight N is N times as likely to be selected as a coupon with weight 1.
- **REQ-268**: If the eligible pool is empty at the time of a win (all coupons expired or none configured), the system shall return a `systemError` response to the frontend and shall not record the play as completed. The player must be able to retry.

**Coupon issuance**

- **REQ-269**: The selected coupon's external identifier, start date, and end date shall be passed to the Coupon API when issuing the reward. The display title and discount value shall be returned to the frontend in the play response.
- **REQ-270**: The frontend shall display the winning coupon's title, discount value, and end date on the result screen. It shall not display weight, internal IDs, or pool metadata.

**Local development seed**

- **REQ-271**: The system shall include a seed script that, when run against a fresh database, inserts a default active campaign and at least one coupon into its pool. The seed shall be idempotent — running it twice must not insert duplicate records.
- **REQ-272**: The seed script shall derive its default values from environment variables (matching the values previously configured via environment variables) so that a developer's existing `.env` file requires no modification for local development.

### Security Requirements

- **SEC-261**: Campaign and coupon pool data must not be exposed in any frontend-accessible API response except for the display fields returned after a win (`title`, `discount`, `endDate`). Internal fields (`weight`, database IDs, `win_probability`) must never be sent to the frontend.
- **SEC-262**: Win probability and coupon selection must be computed server-side. The frontend has no input into which coupon is selected or whether a play results in a win.

### Validation Rules

- **VAL-261**: Win probability must be a decimal value between 0.000 and 1.000 inclusive. Values outside this range must be rejected at the data layer.
- **VAL-262**: Coupon weight must be a positive integer (≥ 1). A weight of 0 or less must be rejected.
- **VAL-263**: A coupon's `end_date` must be strictly after its `start_date`. Records violating this constraint must be rejected.

### Constraints

- **CON-261**: Win probability is a campaign-level attribute. It is not configurable per-coupon or per-player.
- **CON-262**: Coupon weights govern relative selection probability among eligible coupons only — they do not affect the overall win probability.
- **CON-263**: Once a coupon is issued to a player, the record is immutable. Expired or removed coupons in the pool do not retroactively affect previously issued rewards.

### Guidelines

- **GUD-261**: When configuring a coupon pool, operators should ensure at least one coupon remains valid for the full planned duration of the campaign to avoid the empty-pool error state.
- **GUD-262**: Coupon display values (`title`, `discount`) should be sourced from this pool — they should not be duplicated in environment variables once this feature is active.

## 7. Acceptance Criteria

- **AC-261**: Given a campaign has two coupons in its pool (weight 3 and weight 1), when 1,000 play wins are simulated, then the weight-3 coupon is selected approximately 75% of the time and the weight-1 coupon approximately 25% of the time (within acceptable statistical variance).
- **AC-262**: Given a campaign has one coupon whose `end_date` has passed, when a player wins, then the system returns a `systemError` and does not record the play as completed.
- **AC-263**: Given a campaign has one coupon with `start_date` in the future, when a player wins before that date, then the coupon is not selected (treated as ineligible).
- **AC-264**: Given the seed script is run on a fresh database, then the `campaigns` table contains one active campaign and the `campaign_coupons` table contains at least one associated coupon.
- **AC-265**: Given the seed script is run a second time, then no duplicate records are created.
- **AC-266**: Given a player wins, when the play response is returned, then it includes the coupon's `title`, `discount`, and `endDate` — but not its `weight` or internal database ID.
- **AC-267**: Given the campaign's `win_probability` is `0.3`, then approximately 30% of play attempts result in a `win` outcome over a large sample.
- **AC-268**: Given no active campaign exists in the database, when the play endpoint is called, then a `404 CAMPAIGN_NOT_FOUND` error is returned to the frontend.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path — win with pool:** Player wins → backend selects a coupon from the pool → coupon issued → frontend receives coupon display data.
- **Happy path — lose:** Player loses → no coupon selected → `{ outcome: "lose" }` returned.
- **Weighted selection distribution:** Large sample of wins → coupon distribution matches configured weights within statistical tolerance.
- **Single-coupon pool:** Campaign with one coupon → every win issues that coupon.
- **Expired coupon:** All coupons expired → win attempt → `systemError` returned, play not recorded.
- **Future-dated coupon:** Coupon `start_date` in future → not selected as eligible before that date.
- **Mixed pool:** Pool with one active and one expired coupon → only active coupon selected.
- **No active campaign:** `campaigns` table has no `is_active = true` row → play and config requests both return appropriate error.
- **Seed idempotency:** Run seed twice → row counts unchanged.
- **Seed from env:** Default seed uses env var values → local dev works without manual DB setup.
- **Win probability from DB:** `win_probability` updated in DB to 0.0 → no player wins on any play attempt.
- **Win probability from DB:** `win_probability` updated to 1.0 → every play attempt wins.
- **Internal fields not leaked:** Play response inspected → `weight`, campaign `id` beyond what frontend needs, `win_probability` absent from JSON.

## 9. Out of Scope

- An operator UI for managing campaigns or coupon pools — operators interact with the database directly or via a future admin tool.
- Per-player coupon targeting or personalisation — all eligible players in a campaign draw from the same pool.
- Coupon inventory limits (e.g., "only 100 of this coupon available") — all eligible coupons can be issued without a cap.
- Multiple simultaneously active campaigns — exactly one campaign is active at a time.
- Point API integration — this feature covers segment coupons only.
- Campaign scheduling (auto-activate at a future time) — activation is a manual DB update.
- Frontend display of the coupon pool, prize odds, or remaining coupon counts.
