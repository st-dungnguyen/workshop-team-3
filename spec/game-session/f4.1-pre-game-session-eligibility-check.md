# Feature PRD: F4.1 — Pre-Game Session Eligibility Check

## 1. Feature Name

**Pre-Game Session Eligibility Check** — Queries the backend to confirm whether the player is eligible to play before displaying the game board, routing ineligible players to the play-limit screen.

## 2. Epic

- **Parent Epic:** [E4 — Game Session](./_epic-E4-game-session.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

Once the auth gate (E1) confirms the player's identity, the next step before the game board is shown is confirming that the player has a play available for the current window. This feature defines the eligibility check: the API call, the loading state while it is in flight, the routing decision based on the response, and the error handling if the check itself fails.

The eligibility check is invisible to an eligible player — they see a brief loading state and then the game board. For an ineligible player, it is the gate that routes them to the play-limit screen (F4.2) instead.

**Intended Audience:** Engineering team.

**Assumptions:**
- The eligibility check is always performed on WebView load, after E1 confirms a valid token. It cannot be bypassed by navigating directly to the game board route.
- The backend is the sole authority on eligibility. The frontend does not cache the result of a previous eligibility check across sessions or page reloads.
- The backend response indicates one of three states: eligible (can play), ineligible (already played this window), or error (check failed).
- The `GameSession` state on the backend — including `completed` (played, no coupon) and `rewarded` (played, coupon claimed) — informs the eligibility response. The frontend does not need to interpret this state directly; it acts on the eligibility response only.
- The eligibility check uses the player's validated auth token (from E1) to identify the player on the backend.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER (eligible)** | Has not yet played in the current window; passes the check and is shown the game board |
| **PLAYER (ineligible)** | Has already played (won or lost) in the current window; is routed to the play-limit screen (F4.2) |
| **SYSTEM** | Receives the eligibility request, evaluates the player's `GameSession` history, and returns an eligibility status |

## 5. User Stories

- As a **PLAYER who has not yet played today**, I want the eligibility check to be invisible and fast so that I arrive at the game board without friction.
- As a **PLAYER who has already played today**, I want to know immediately — without reaching the game board — that I've used my play for the day, so that I'm not confused or frustrated.
- As a **PLAYER experiencing a network error**, I want a retry option so that a transient failure doesn't prevent me from playing.

## 6. Requirements

### Functional Requirements

- **REQ-411**: Upon successful token validation (E1), the system shall immediately initiate an eligibility check request to the backend, including the player's validated auth token.
- **REQ-412**: While the eligibility check request is in flight, the system shall display a loading indicator. The game board must not be rendered or accessible during this time.
- **REQ-413**: When the backend responds that the player is eligible, the system shall transition to and display the game board (E2).
- **REQ-414**: When the backend responds that the player is ineligible (already played this window), the system shall transition to the play-limit screen (F4.2) without displaying the game board.
- **REQ-415**: When the backend returns a server error (500 or 503) during the eligibility check, the system shall display a `game.sessionCheckError` screen with a retry button.
- **REQ-416**: When the player taps retry on the `game.sessionCheckError` screen, the system shall re-submit the eligibility check request.
- **REQ-417**: When the backend returns a 401 response during the eligibility check, the system shall display the `auth.unauthorized` error screen — the session token has expired and the player must re-open the WebView.

### Security Requirements

- **SEC-411**: The eligibility check request shall include the player's validated auth token so the backend can identify the player. The token must not be derived from local storage or any source other than the in-memory value held by E1.
- **SEC-412**: The frontend must not allow the game board to be reached by navigating directly to its route without a successful eligibility response in the current session load. The eligibility check must be enforced at the routing level, not just as a UI guard.

### Validation Rules

- **VAL-411**: The system shall not proceed to the game board if the eligibility check has not completed with a confirmed eligible response in the current session. A pending or failed check must block access.

### Constraints

- **CON-411**: The result of a previous eligibility check (from an earlier WebView session or page load) must not be used. The check is always fresh on load.
- **CON-412**: The loading state shown during the eligibility check must not expose the game board UI beneath it — the board must not be pre-rendered and then hidden; it must not exist in the DOM until eligibility is confirmed.

### Guidelines

- **GUD-411**: The eligibility check loading state should be visually consistent with the auth loading state from E1 — the player experiences a single, smooth loading sequence that transitions from auth to eligibility to the game board.
- **GUD-412**: Loading text, if shown, should be neutral (e.g., "読み込み中..." / `common.loading`) — it does not need to mention "eligibility" or "checking sessions" to the player.

## 7. Acceptance Criteria

- **AC-411**: Given the player's token has been validated (E1 complete), then an eligibility check request is sent to the backend before the game board is rendered.
- **AC-412**: Given the eligibility check is in flight, then a loading indicator is visible and the game board is not accessible.
- **AC-413**: Given the backend responds with an eligible status, then the game board is displayed and the player can initiate a play session.
- **AC-414**: Given the backend responds with an ineligible status, then the play-limit screen (F4.2) is shown and the game board is not accessible.
- **AC-415**: Given the backend returns a 500 error during the eligibility check, then a `game.sessionCheckError` screen appears with a retry button — the game board is not shown.
- **AC-416**: Given the `game.sessionCheckError` screen is shown, when the player taps retry and the backend returns eligible, then the game board is displayed.
- **AC-417**: Given the backend returns 401 during the eligibility check, then the `auth.unauthorized` screen is shown — not `game.sessionCheckError`.
- **AC-418**: Given the player navigates directly to the game board route (bypassing the WebView entry flow), then the eligibility check is still enforced — the game board does not render without a confirmed eligible response.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path (eligible):** Token validated → eligibility check sent → backend returns eligible → game board shown.
- **Ineligible:** Token validated → eligibility check sent → backend returns ineligible → play-limit screen shown (F4.2), no game board.
- **Server error (500/503):** Eligibility check returns 500 → `game.sessionCheckError` shown with retry.
- **Retry on error:** Error screen → player taps retry → backend returns eligible → game board shown.
- **Retry on repeated error:** Multiple retries, error persists each time → error screen stays, no game board.
- **401 during check:** Backend returns 401 → `auth.unauthorized` shown (not session error).
- **Direct route access:** Player navigates directly to game board URL → eligibility check still fires, game board not shown until check passes.
- **Game board hidden during load:** During eligibility check, game board DOM elements must not be present or accessible — inspect DOM during loading state.
- **Loading state visible:** A loading indicator is visible from start of eligibility check until response — no blank white screen.
- **Locale:** All eligibility error strings display in `ja` by default; switch to `en` updates all strings.
- **Token source:** Eligibility request includes the in-memory token from E1 — not a token read from localStorage.
- **App backgrounded during check:** Player backgrounds the native app while eligibility check is in flight → on resume, check result is handled correctly (no crash, no double-request).

## 9. Out of Scope

- Determining the play-limit window duration (once per day, once per campaign) — the backend decides; the frontend only acts on the response.
- Displaying when the next play window opens — that is the responsibility of F4.2, which receives this information from the eligibility response.
- Caching or locally persisting the eligibility result across page loads or WebView sessions.
- Retrying the eligibility check automatically without player action — retries are always player-initiated.
- Game session history display (past wins, past losses).
