# Feature PRD: F4.2 — Play Limit & Cooldown Screen

## 1. Feature Name

**Play Limit & Cooldown Screen** — A warm, branded screen shown to players who have already used their play for the current window, communicating when they can return and play again.

## 2. Epic

- **Parent Epic:** [E4 — Game Session](./_epic-E4-game-session.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

When the eligibility check (F4.1) confirms that the player has already played in the current window, this feature defines what the player sees instead of the game board. The play-limit screen is not an error — it is an expected, designed state in the campaign experience. Its job is to acknowledge the player's participation, tell them when they can return, and send them back to the native app without frustration.

The tone is warm and encouraging, consistent with the Japanese food-brand aesthetic and the "see you tomorrow" spirit of a daily campaign. A player who loses and returns tomorrow is still a successful campaign outcome.

**Intended Audience:** Engineering team.

**Assumptions:**
- The play-limit screen is only reached via F4.1 routing — never directly navigated to.
- The backend eligibility response may include a `nextPlayAt` timestamp indicating when the current window expires. The screen should display this when available.
- Both win outcomes (rewarded) and lose outcomes (completed) result in the same play-limit screen — the outcome of the previous play is not shown on this screen. The message is forward-looking, not backward-looking.
- The player can close the WebView from this screen using the standard close mechanism (`{webViewHost}/close`).
- This screen has no interactive elements beyond a close/return CTA.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER (already played — win)** | Claimed their coupon and re-opened the WebView; should be warmly acknowledged and directed to come back tomorrow |
| **PLAYER (already played — lose)** | Played and lost; should receive an encouraging message that motivates them to return, not a discouraging "you lost, try again tomorrow" |
| **HOST** | The native app; intercepts the close action when the player taps the return CTA |

## 5. User Stories

- As a **PLAYER who has already played today**, I want to understand immediately that I've used my daily play so that I'm not confused about why the game isn't loading.
- As a **PLAYER**, I want to know when I can play again so that I have a reason to return to the app.
- As a **PLAYER who lost**, I want an encouraging message that makes me feel motivated to try again tomorrow rather than discouraged.
- As a **PLAYER who already won**, I want a positive acknowledgment so that the experience of having won feels complete and satisfying.

## 6. Requirements

### Functional Requirements

- **REQ-421**: When the eligibility check (F4.1) returns an ineligible response, the system shall display the play-limit screen instead of the game board.
- **REQ-422**: The play-limit screen shall display a localized message informing the player that their play for the current window has been used (e.g., "本日の挑戦はお済みです" / `game.alreadyPlayed`).
- **REQ-423**: If the backend eligibility response includes a `nextPlayAt` timestamp, the system shall display a localized message indicating when the player can play again (e.g., "明日またチャレンジしよう！" with the date, or the time remaining / `game.nextPlayAt`).
- **REQ-424**: If the `nextPlayAt` timestamp is not provided in the eligibility response, the system shall display a generic "come back soon" message without a specific date or time (`game.comeBackSoon`).
- **REQ-425**: The play-limit screen shall display a primary CTA to close the WebView and return to the native app.
- **REQ-426**: When the player taps the close CTA, the system shall navigate to `{webViewHost}/close` to close the WebView.
- **REQ-427**: The play-limit screen must not display a game board, a spin button, a scratch card, or any other game UI element. The game must be completely absent from this screen.

### Constraints

- **CON-421**: The play-limit screen must not offer a replay option or any mechanism to bypass the play limit within the current window. There is no "try again" button on this screen.
- **CON-422**: The play-limit screen must not display the outcome of the player's previous session (whether they won or lost). The message is forward-looking only.
- **CON-423**: The close CTA on the play-limit screen must navigate to `{webViewHost}/close`. The `sklgusto://close` scheme must not be used (not yet available as of 2026-08).

### Guidelines

- **GUD-421**: The play-limit screen should feel like a natural pause in the campaign, not a wall. The visual design should use warm, friendly imagery consistent with the Japanese food-brand aesthetic — the same tonal warmth as the result screen's lose state.
- **GUD-422**: The message copy should be encouraging and forward-looking. Examples:
  - "また明日チャレンジしよう！" ("Challenge again tomorrow!" — `game.comeBackTomorrow`)
  - "明日 {date} からまた遊べます！" ("You can play again from {date}!" — `game.nextPlayAt`)
  - Avoid phrasing that sounds punishing, limiting, or corporate (e.g., "本日の利用上限に達しました" is too mechanical).
- **GUD-423**: If the `nextPlayAt` timestamp includes a specific time (not just a date), display the time in the user's local timezone. Do not display raw UTC timestamps.
- **GUD-424**: The close CTA should be clearly labeled and prominent (e.g., "アプリに戻る" / `game.returnToApp`), with a minimum touch target of 44px height.

## 7. Acceptance Criteria

- **AC-421**: Given the eligibility check returns ineligible, then the play-limit screen is displayed and no game board UI is visible.
- **AC-422**: Given the play-limit screen is shown, then a localized "already played" message is visible in the current locale.
- **AC-423**: Given the eligibility response includes a `nextPlayAt` timestamp, then the play-limit screen displays a localized message indicating when the next play window opens — formatted for the player's locale (not raw UTC).
- **AC-424**: Given the eligibility response does not include a `nextPlayAt` timestamp, then the play-limit screen displays a generic "come back soon" message without a specific time reference.
- **AC-425**: Given the play-limit screen is shown, when the player taps the close CTA, then the WebView navigates to `{webViewHost}/close`.
- **AC-426**: Given the play-limit screen is shown, then no replay button, spin button, scratch card, or game UI element is visible or accessible.
- **AC-427**: Given the play-limit screen is shown in `ja` locale, then all text — "already played" message, next-play message, close CTA — is in Japanese.
- **AC-428**: Given the play-limit screen is shown and locale is switched to `en`, then all text updates to English.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Ineligible routing:** F4.1 returns ineligible → play-limit screen shown, game board absent (not in DOM).
- **nextPlayAt present:** Eligibility response includes `nextPlayAt` → screen shows formatted date/time in correct locale — not raw ISO string or UTC.
- **nextPlayAt absent:** Eligibility response omits `nextPlayAt` → generic "come back soon" message shown, no broken placeholder.
- **nextPlayAt formatting — ja:** Timestamp displayed in Japanese date format (e.g., "8月7日（木）") in correct local timezone.
- **nextPlayAt formatting — en:** Same timestamp displayed in English format (e.g., "Thursday, August 7") in correct local timezone.
- **Close CTA — iOS:** Player taps "アプリに戻る" → WebView closes via `{webViewHost}/close`.
- **Close CTA — Android:** Same close behavior on Android.
- **No game UI on screen:** Inspect DOM → no spin button, no scratch card, no wheel canvas; game components not rendered.
- **No replay bypass:** No button, link, or navigation path from the play-limit screen leads back to the game board in the same WebView session.
- **Locale — ja (default):** All strings on play-limit screen in Japanese.
- **Locale — en:** Locale switch updates all strings to English.
- **Visual design:** Play-limit screen is warm and encouraging — no red colors, no error iconography, no mechanical "limit reached" language.
- **Touch target:** Close CTA meets 44px minimum height.
- **Re-open after playing:** Player plays (wins or loses), exits WebView, re-opens WebView → eligibility check runs → play-limit screen shown (same window).
- **Re-open after window reset:** Player re-opens WebView after the play window resets → eligibility check runs → game board shown (eligible again).

## 9. Out of Scope

- Determining when the play window resets — the backend decides; the frontend only uses the `nextPlayAt` value if provided.
- Displaying the outcome of the player's previous session on the play-limit screen.
- Notifying the player (push notification, email) when the next play window opens — native app concern.
- Showing a history of past sessions (wins, losses, coupon history) within the WebView.
- Any mechanism to purchase additional plays or extend the play window.
- Countdown timer showing time remaining until the next play — the spec requires showing the next-play date/time, not a live countdown. A countdown is a future enhancement.
