# Feature PRD: F1.1 — URL Query Param Token Reception

## 1. Feature Name

**URL Query Param Token Reception** — Enables the WebView to extract an auth token delivered by the native app as a URL query parameter at launch time.

## 2. Epic

- **Parent Epic:** [E1 — Auth Bridge](./_epic-E1-auth-bridge.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

When the native app opens the WebView, it may append a JWT to the URL as `?accessToken=<jwt>`. This is the simpler of the two delivery channels and may be the primary mechanism on older native app versions. The WebView must detect and extract this token on initial load and make it available to the auth gate ([F1.3](./f1.3-token-validation-and-game-access-gate.md)).

**Intended Audience:** Engineering team.

**Assumptions:**
- The query parameter key is exactly `accessToken` (camelCase).
- The token value is a non-empty, URL-encoded JWT string.
- If both URL param and JS bridge deliver a token, F1.3 governs which takes precedence.
- The WebView has no control over whether the native app includes the parameter — the WebView must handle both its presence and absence gracefully.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Opens the WebView from the native app; unaware of how the token is delivered — expects to land on the game |
| **HOST** | Constructs the WebView URL with `?token=<jwt>` appended and opens it in the embedded browser |

## 5. User Stories

- As a **HOST**, I want to deliver an auth token via the WebView URL so that the player is authenticated automatically on arrival without a login screen.
- As a **PLAYER**, I want the app to recognize who I am as soon as I open the game so that I can start playing immediately.

## 6. Requirements

### Functional Requirements

- **REQ-101**: The system shall inspect the WebView URL for an `accessToken` query parameter on initial page load.
- **REQ-102**: When an `accessToken` parameter is present and non-empty, the system shall extract its value and pass it to the auth validation flow (F1.3).
- **REQ-103**: When the `accessToken` parameter is absent or empty, the system shall not treat this as an error at the reception stage — it shall check localStorage for a previously validated token (F1.3) before falling back to the JS bridge channel (F1.2).

### Security Requirements

- **SEC-101**: The system shall not log, display, or expose the raw token value in any user-visible surface (UI, console output in production).

### Constraints

- **CON-101**: Token extraction must occur on initial page load only. Tokens present in the URL after navigation events (if any) shall be ignored.
- **CON-102**: The system shall not redirect to a URL that strips the token in a way that could cause a reload loop.

### Guidelines

- **GUD-101**: The system should handle URL-encoded token values transparently, decoding them before passing to the validation flow.

## 7. Acceptance Criteria

- **AC-101**: Given the WebView is opened with `?accessToken=<valid-jwt>` in the URL, when the page loads, then the token value is extracted and passed to the auth validation flow without the player seeing a loading error.
- **AC-102**: Given the WebView is opened without an `accessToken` query parameter, when the page loads, then the system does not show a token error immediately and instead checks localStorage then waits for the JS bridge channel.
- **AC-103**: Given the WebView is opened with `?accessToken=` (empty value), when the page loads, then the system treats this equivalently to a missing parameter.
- **AC-104**: Given the WebView is opened with a URL-encoded token value, when the page loads, then the token is correctly decoded and passed to the validation flow unchanged.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path:** WebView opened with a valid `?accessToken=<jwt>` — token is extracted and auth proceeds to F1.3.
- **Missing param:** WebView opened without `?accessToken` — system checks localStorage, then waits for JS bridge (no premature error).
- **Empty param:** WebView opened with `?accessToken=` — treated the same as missing.
- **URL-encoded value:** Token containing `+`, `%3D`, etc. — correctly decoded before validation.
- **Token in wrong param name** (e.g., `?token=` or `?auth_token=`): not extracted; system falls through to localStorage / JS bridge.
- **Security:** Raw token value does not appear in any console log or UI element in a production build.

## 9. Out of Scope

- Delivering or constructing the token URL — that is the HOST's responsibility.
- Validating the token format or signature at this stage — handled by F1.3.
- Handling tokens in URL hash fragments or request headers.
- Stripping the token from the URL after extraction (a UX-only concern with no security implication in a WebView with no address bar).
