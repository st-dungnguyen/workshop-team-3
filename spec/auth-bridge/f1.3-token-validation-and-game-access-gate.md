# Feature PRD: F1.3 — Token Validation & Game Access Gate

## 1. Feature Name

**Token Validation & Game Access Gate** — Validates the received token with the backend and controls whether the player may access the game, displaying appropriate error screens for every failure mode.

## 2. Epic

- **Parent Epic:** [E1 — Auth Bridge](./_epic-E1-auth-bridge.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

Once a token is received (from F1.1 or F1.2), the WebView must confirm its validity with the backend before the player can access any game screen. This feature is the enforcement point of the auth gate: no player reaches the game without a validated identity. It also owns all error and recovery UX for every auth failure mode.

**Intended Audience:** Engineering team.

**Assumptions:**
- Token validation is performed by submitting the token to the project backend (not to the Coupon API directly).
- The backend response determines whether the token is valid, expired, or unauthorized.
- The frontend cannot decode or inspect the token's claims itself — validation is server-authoritative.
- If both URL param and JS bridge provide a token, the first token received by the system is submitted for validation. A subsequent token from the other channel is not retried unless the user triggers a manual retry.
- The player has no way to "log in again" from within the WebView — the only recovery path for auth failures is to re-open the WebView from the native app.
- All error screen strings must exist in both `ja` and `en` locale files (`auth.json`).

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Expects to arrive at the game immediately; if auth fails, needs a clear explanation of what happened and what to do next |
| **HOST** | Responsible for providing a fresh, valid token; may re-open the WebView with a new token if the player requests it |
| **SYSTEM** | The project backend; authoritative source for token validity; returns structured error codes the frontend acts upon |

## 5. User Stories

- As a **PLAYER**, I want the game to be available immediately after I open it so that I don't have to wait or log in.
- As a **PLAYER**, I want a clear message when something goes wrong with my session so that I know whether to try again or go back to the app.
- As a **HOST**, I want the WebView to reject invalid or expired tokens so that unauthorized players cannot access the game.
- As a **SYSTEM**, I want to be the sole authority on token validity so that the frontend cannot be tricked by a manipulated token.

## 6. Requirements

### Functional Requirements

- **REQ-301**: The system shall display a loading screen immediately upon receiving a token from either channel (F1.1 or F1.2), before the validation response is received.
- **REQ-302**: The system shall submit the received token to the backend validation endpoint and await the response before rendering any game screen.
- **REQ-303**: When the backend confirms the token is valid, the system shall grant the player access to the game and navigate to the game entry screen.
- **REQ-304**: When no token is received from either channel within the designated wait period, the system shall display the `auth.tokenMissing` error screen.
- **REQ-305**: When the backend returns a token-expired error, the system shall display the `auth.tokenExpired` error screen.
- **REQ-306**: When the backend returns a token-invalid or signature-failure error, the system shall display the `auth.tokenInvalid` error screen.
- **REQ-307**: When the backend returns a 401 Unauthorized response, the system shall display the `auth.unauthorized` error screen.
- **REQ-308**: When the backend returns a 500 or 503 response, the system shall display the `auth.serverError` error screen with a manual retry option.
- **REQ-309**: The validated token shall be held in memory (auth context) for the lifetime of the current WebView session only.

### Security Requirements

- **SEC-301**: The system shall never grant game access based on client-side inspection of the token (e.g., decoding the JWT payload). Validation is server-authoritative.
- **SEC-302**: The token shall not be written to localStorage, sessionStorage, cookies, or any other persistent storage at any point.
- **SEC-303**: The token shall be cleared from memory when the WebView is closed or the page is unloaded.
- **SEC-304**: Error screens must not expose the raw token value or backend error internals to the player.

### Validation Rules

- **VAL-301**: A token that is structurally empty or null shall not be submitted to the backend; the system shall treat it as a missing token (REQ-304).
- **VAL-302**: The system shall submit only the first valid non-empty token received; subsequent tokens from the other channel shall not trigger a second validation unless the first has definitively failed and the player triggers a retry.

### Constraints

- **CON-301**: There is no in-WebView re-authentication flow. Every error screen (except server error with retry) instructs the player to close the WebView and re-open it from the native app.
- **CON-302**: The game access gate is absolute — there is no debug mode, bypass flag, or grace period that allows game access with an unvalidated token.

### Guidelines

- **GUD-301**: The loading screen should be visually consistent with the game's warm Japanese aesthetic to avoid a jarring transition.
- **GUD-302**: Error screens should be friendly and non-technical — "お時間が経過しました。アプリからもう一度お試しください。" rather than "401 Unauthorized".

## 7. Acceptance Criteria

- **AC-301**: Given a valid token is received, when validation completes successfully, then the player lands on the game entry screen without any additional confirmation step.
- **AC-302**: Given a token is received, when the backend responds that the token is expired, then the system displays the `auth.tokenExpired` screen (localized in `ja`) and does not show any game content.
- **AC-303**: Given a token is received, when the backend returns 401, then the system displays the `auth.unauthorized` screen and does not show any game content.
- **AC-304**: Given a token is received, when the backend returns 500 or 503, then the system displays the `auth.serverError` screen with a visible retry button; tapping retry re-submits the same token for validation.
- **AC-305**: Given neither URL param nor JS bridge has delivered a token within the wait period, when the wait period elapses, then the system displays the `auth.tokenMissing` screen.
- **AC-306**: Given a player is on the `auth.serverError` screen, when they tap retry and validation now succeeds, then the player is navigated to the game entry screen.
- **AC-307**: Given a player is on any auth error screen, when they inspect the page, then no raw token value is visible in the UI or accessible via browser developer tools.
- **AC-308**: Given the WebView is closed (navigated to `/close`), when the page unloads, then the token is no longer held in memory.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path (URL param):** Valid token via URL → loading screen → game entry screen.
- **Happy path (JS bridge):** Valid token via bridge message → loading screen → game entry screen.
- **Happy path (both channels):** Token via URL arrives first; bridge token arrives later → first token used, game loads correctly.
- **Token expired:** Backend returns expired error → `auth.tokenExpired` screen shown, no game content visible.
- **Token invalid signature:** Backend returns invalid error → `auth.tokenInvalid` screen shown.
- **Unauthorized:** Backend returns 401 → `auth.unauthorized` screen shown.
- **Server error with retry:** Backend returns 500 → `auth.serverError` screen with retry button; retry succeeds → game loads.
- **Token missing:** Page loads, neither channel delivers a token within the wait period → `auth.tokenMissing` screen.
- **Empty token:** `?token=` in URL, no bridge message → treated as missing (wait period starts).
- **Security — no persistence:** After a successful auth, reload the page → token is gone, auth restarts.
- **Security — no bypass:** Directly navigating to the game URL without a token → redirected to auth gate, not the game.
- **Locale:** All error screens render in `ja` by default; switch to `en` locale → all strings update correctly.
- **Retry on server error:** 503 → retry → 200 → game entry screen.

## 9. Out of Scope

- Token refresh or silent re-authentication mid-session.
- Differentiating between a token that is structurally malformed (bad JWT format) versus cryptographically invalid — both map to `auth.tokenInvalid` from the frontend's perspective.
- Showing game content while validation is pending (optimistic rendering).
- Any analytics or logging of auth failure rates — that is a backend/observability concern.
- Deep-linking to a specific game state via the token or URL params other than `token`.
