# Feature PRD: F1.2 — JS Bridge Token Reception

## 1. Feature Name

**JS Bridge Token Reception** — Enables the WebView to receive an auth token delivered by the native app through a JavaScript messaging bridge after page load.

## 2. Epic

- **Parent Epic:** [E1 — Auth Bridge](./_epic-E1-auth-bridge.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

Some native app implementations deliver the auth token after the WebView has finished loading, rather than embedding it in the URL. The WebView must listen for an incoming message of a specific structure and extract the token from it. This channel handles cases where the URL channel is unavailable, and acts as the fallback (or primary, depending on the host app version).

**Intended Audience:** Engineering team.

**Assumptions:**
- The HOST sends a message with the structure `{ type: "AUTH_TOKEN", token: "<jwt>" }`.
- The message may arrive at any point from page load until the player exits the WebView.
- Both iOS and Android native apps use the same message format and delivery mechanism.
- Messages of any other `type` value must be silently ignored — the bridge may carry messages unrelated to auth.
- If the URL param channel ([F1.1](./f1.1-url-query-param-token.md)) has already provided a token, a subsequent JS bridge message with a new token shall be ignored (first-received-wins policy, governed by F1.3).

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Opens the WebView from the native app; unaware of token delivery — expects to land on the game |
| **HOST** | Sends a JS bridge message containing the JWT after the WebView has loaded |

## 5. User Stories

- As a **HOST**, I want to deliver an auth token via a JS bridge message so that even if the WebView URL cannot carry the token, the player is still authenticated automatically.
- As a **PLAYER**, I want the game to recognize me regardless of how my token was delivered, so that my experience is seamless on all native app versions.

## 6. Requirements

### Functional Requirements

- **REQ-201**: The system shall register a message listener on page load that listens for messages from the native app host.
- **REQ-202**: When a message arrives with `type` equal to `"AUTH_TOKEN"` and a non-empty `token` field, the system shall extract the token value and pass it to the auth validation flow (F1.3).
- **REQ-203**: When a message arrives with any `type` other than `"AUTH_TOKEN"`, the system shall ignore it without error.
- **REQ-204**: When a message arrives with `type` equal to `"AUTH_TOKEN"` but an absent or empty `token` field, the system shall treat it as a malformed delivery and not attempt validation with an empty token.
- **REQ-205**: The message listener shall remain active from page load until the WebView is closed or navigated away.

### Security Requirements

- **SEC-201**: The system shall only accept bridge messages that conform to the expected structure (`{ type, token }`). Malformed payloads shall be discarded without any side effects.
- **SEC-202**: The system shall not log, display, or expose the raw token value in any user-visible surface (UI, console output in production).
- **SEC-203**: The system shall not write the token to localStorage, sessionStorage, cookies, or any persistent storage at any point during extraction.

### Validation Rules

- **VAL-201**: A `token` value consisting only of whitespace shall be treated as empty and rejected at the reception stage.

### Constraints

- **CON-201**: If a valid token has already been received via the URL param channel (F1.1) and validated successfully, a subsequent JS bridge `AUTH_TOKEN` message shall not replace the active token mid-session.

### Guidelines

- **GUD-201**: The system should handle the case where the bridge message arrives before or after the URL param is processed — the outcome must be the same regardless of delivery order.

## 7. Acceptance Criteria

- **AC-201**: Given the WebView is open and no token has been received yet, when the HOST sends `{ type: "AUTH_TOKEN", token: "<valid-jwt>" }`, then the token is extracted and passed to the auth validation flow.
- **AC-202**: Given the WebView receives a message with `type: "SOME_OTHER_EVENT"`, when the message listener processes it, then no token extraction or auth action occurs.
- **AC-203**: Given the WebView receives `{ type: "AUTH_TOKEN", token: "" }`, when the message listener processes it, then no validation attempt is made and the system continues waiting.
- **AC-204**: Given a valid token has already been received via URL param and validated, when the HOST subsequently sends a JS bridge `AUTH_TOKEN` message with a different token, then the active session token is not replaced.
- **AC-205**: Given the WebView is open and listening, when the HOST sends the bridge message 3 seconds after page load, then the token is received and processed correctly (no race condition on the listener).

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path:** Bridge message arrives after page load with a valid token — extracted and passed to F1.3.
- **Early message:** Bridge message arrives before page has fully mounted its listener — token must not be missed.
- **Ignored message types:** Messages with `type` other than `AUTH_TOKEN` — no side effects.
- **Malformed payload:** `{ type: "AUTH_TOKEN" }` (missing `token`), `{ type: "AUTH_TOKEN", token: "" }`, `{ token: "abc" }` (missing `type`) — all discarded.
- **Both channels active:** URL param token arrives first, then JS bridge token — first token wins, session is not disrupted.
- **JS bridge only:** No URL param present, bridge delivers token after 2s delay — works correctly.
- **Security:** Token value not visible in production console or UI.

## 9. Out of Scope

- Determining which native app version uses which channel — that is the HOST's concern.
- Sending messages back to the native app via the bridge — covered separately if needed (e.g., close command).
- Validating the token format or signature at this stage — handled by F1.3.
- Supporting token delivery via `postMessage` from an untrusted iframe or cross-origin source.
