# Feature PRD: F3.1 — Win Recording & Coupon Issuance

## 1. Feature Name

**Win Recording & Coupon Issuance** — Enables the WebView to submit a win result to the project backend and receive a coupon identifier in return, completing the `GameSession` lifecycle to `rewarded`.

## 2. Epic

- **Parent Epic:** [E3 — Reward/Coupon](./_epic-E3-reward-coupon.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

When the player wins a game session, the result screen (F2.3) presents a claim CTA. Tapping it triggers this feature: the frontend submits the win to the project backend, which validates it and issues a segment coupon on the player's behalf. The backend returns a `couponId`, which the frontend holds in memory and passes to F3.2 for delivery.

This is the most sensitive step in the reward flow — a failure here means the player wins but receives nothing. Robust error handling and retry are critical.

**Intended Audience:** Engineering team.

**Assumptions:**
- The win signal is received from [F2.3](../game-core/f2.3-game-result-screen.md). F3.1 is not triggered directly by the player — it is triggered by the result screen's claim CTA.
- The project backend (not the Coupon API) is the call target. The backend validates the win, calls `POST /segment` on the Coupon API server-side, and returns the `couponId`.
- The player's validated token (from E1) is sent with the win record request so the backend can identify the player.
- The backend is idempotent for the same `sessionId` — calling win-record twice for the same session returns the same `couponId`, not a duplicate coupon.
- The `couponId` is held in memory for the current WebView session only — it is not persisted to any storage.
- After the `couponId` is received, the `GameSession` transitions to `rewarded`.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Has just seen the win result screen; taps the claim CTA expecting to receive their coupon immediately |
| **SYSTEM** | Receives the win record, validates session eligibility, issues the segment coupon, and returns the `couponId` |

## 5. User Stories

- As a **PLAYER who won**, I want to claim my coupon with a single tap so that I can receive my reward without additional steps.
- As a **PLAYER**, I want to see a clear loading state while my coupon is being prepared so that I know the system is working.
- As a **PLAYER**, I want a retry option if something goes wrong so that a temporary server issue doesn't cost me my reward.
- As a **SYSTEM**, I want win records to include the player's identity and session ID so that I can validate eligibility and prevent duplicate issuance.

## 6. Requirements

### Functional Requirements

- **REQ-301**: When the player taps either the "Claim Coupon" or "Use Now" CTA on the win result screen, the system shall capture the CTA intent (`claimCoupon` or `useNow`) and submit a win record request to the project backend, including the player's session identifier and validated auth token. The win-recording API call is identical regardless of which CTA was tapped.
- **REQ-302**: While the win record request is in flight, the system shall display a loading indicator and disable both CTAs to prevent duplicate submissions.
- **REQ-303**: When the backend responds with a `couponId`, the system shall hold the `couponId` in memory, hold the CTA intent in memory, and transition the `GameSession` to `rewarded`.
- **REQ-304**: After transitioning to `rewarded`, the system shall immediately proceed to coupon delivery (F3.2), passing both the `couponId` and the CTA intent, without requiring an additional player action.
- **REQ-305**: When the backend returns a server error (500 or 503), the system shall display the `reward.claimError` screen with a retry button. The `GameSession` shall remain in `completed` (not `rewarded`) until a successful response is received.
- **REQ-306**: When the player taps retry on the `reward.claimError` screen, the system shall re-submit the win record request.
- **REQ-307**: When the backend returns a duplicate-win response (the coupon was already issued for this session), the system shall treat this as a success — use the `couponId` from the response and proceed to F3.2.
- **REQ-308**: When the backend returns a 401 response, the system shall display the `auth.unauthorized` error screen — the session token has expired and the player must re-open the WebView from the native app.

### Security Requirements

- **SEC-301**: The win record request shall include the player's validated auth token so the backend can verify the player's identity before issuing a coupon.
- **SEC-302**: The `couponId` shall be held in memory only. It must not be written to localStorage, sessionStorage, or cookies.
- **SEC-303**: The frontend must not attempt to call the Coupon API (`POST /segment`) directly. All coupon issuance must go through the project backend.

### Validation Rules

- **VAL-301**: Both "Claim Coupon" and "Use Now" CTAs shall only be active when the `GameSession` is in `completed` state with outcome `win`. They must not be triggerable from a `lose` result or from any other session state.

### Constraints

- **CON-301**: Both CTAs ("Claim Coupon" and "Use Now") must be disabled while a win record request is in flight. Re-enabling happens only after a definitive success or error response is received.
- **CON-302**: The `GameSession` shall not transition to `rewarded` until the backend confirms the coupon has been issued (i.e., a `couponId` is received). A failed or pending request does not advance the session.

### Guidelines

- **GUD-301**: The loading state during win recording should reassure the player their coupon is being prepared — e.g., an animated indicator with a localized message like "クーポンを準備しています..." (`reward.issuingCoupon`).
- **GUD-302**: The retry button on `reward.claimError` should be prominent and clearly labeled — e.g., "もう一度試す" (`reward.retry`). The win confirmation message should remain visible on the error screen so the player knows they did win.

## 7. Acceptance Criteria

- **AC-301**: Given the player is on the win result screen, when they tap the claim CTA, then a loading indicator appears, the CTA is disabled, and a win record request is sent to the backend.
- **AC-302**: Given the win record request succeeds and the backend returns a `couponId`, then the `GameSession` transitions to `rewarded` and F3.2 is immediately triggered.
- **AC-303**: Given the backend returns a 500 error, then the `reward.claimError` screen is shown with a retry button, and the `GameSession` remains in `completed` state.
- **AC-304**: Given the `reward.claimError` screen is shown, when the player taps retry and the backend returns a `couponId`, then the `GameSession` transitions to `rewarded` and F3.2 is triggered.
- **AC-305**: Given the player taps the claim CTA twice in rapid succession, then only one win record request is sent to the backend (CTA disabled after first tap).
- **AC-306**: Given the backend returns a duplicate-win response with a `couponId`, then the system treats it as a success and proceeds to F3.2 with that `couponId`.
- **AC-307**: Given the backend returns 401, then the `auth.unauthorized` screen is shown and the reward flow does not continue.
- **AC-308**: Given a `couponId` is received, then it is not written to localStorage, sessionStorage, or any browser storage — it exists only in memory for the current session.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path:** Claim CTA tapped → loading shown, CTA disabled → backend returns `couponId` → session `rewarded` → F3.2 triggered.
- **Server error (500/503):** Backend returns 500 → `reward.claimError` shown with retry → retry returns `couponId` → success path.
- **Retry on error:** Error shown → player taps retry → success → F3.2 triggered.
- **Retry on repeated error:** Player retries multiple times → error persists each time → error screen remains, no session state change.
- **Double-tap prevention:** Two rapid taps on claim CTA → only one request sent.
- **Duplicate win:** Backend returns duplicate-win with `couponId` → treated as success, F3.2 proceeds.
- **401 on win record:** Backend returns 401 → `auth.unauthorized` shown, not `reward.claimError`.
- **Security — no Coupon API direct call:** Network traffic shows no direct call to `coupon-api-*.skylark.co.jp` from the frontend.
- **Security — no storage:** After win recording, `couponId` absent from localStorage, sessionStorage, cookies.
- **Session state:** After 500 error, `GameSession` remains `completed`, not `rewarded`; after success, transitions to `rewarded`.
- **Locale:** Loading message, error message, retry button all display in `ja` by default; `en` switch updates all strings.

## 9. Out of Scope

- The mechanics of coupon issuance on the backend (calling `POST /segment` on the Coupon API) — that is SYSTEM's responsibility.
- Displaying coupon details (name, discount amount, expiry) within the WebView — handled by the native app after AppLink navigation (F3.2).
- Coupon validation or redemption at point of purchase — native app concern.
- Retrying indefinitely or with exponential backoff — the retry is manual (player-initiated).
- Logging win events for analytics purposes.
