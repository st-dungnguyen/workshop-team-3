# Feature PRD: F3.1 — Auto Background Coupon Claim

## 1. Feature Name

**Auto Background Coupon Claim** — Automatically triggers coupon issuance on the project backend as a fire-and-forget call immediately when a winning play result is received, without requiring any player action or blocking the win screen.

## 2. Epic

- **Parent Epic:** [E3 — Reward/Coupon](./_epic-E3-reward-coupon.md)
- **Priority:** P0 — Critical

## 3. Purpose & Scope

When the `play()` API returns `outcome: 'win'`, the frontend immediately fires a background claim request (`POST /game/claim`) to the project backend. The backend uses this signal to validate the win and issue a segment coupon on the player's behalf via the Coupon API. This call is fire-and-forget: the frontend does not wait for a response, does not show a loading state, and does not surface errors to the player.

The `couponId` needed for subsequent AppLink navigation is provided directly in the `play()` response — not in the claim response. The claim call's sole purpose is to notify the backend to finalize coupon issuance. This decoupling ensures the win screen appears immediately and the player is never blocked by the claim network round-trip.

**Intended Audience:** Engineering team.

**Assumptions:**
- The `play()` API response includes `coupon.id` when `outcome === 'win'`. This ID is held in memory and passed to F3.2 for AppLink construction.
- The project backend's `POST /game/claim` endpoint is idempotent for the same session — calling it multiple times (e.g., if a retry fires) does not issue duplicate coupons.
- The frontend does not need to confirm that the claim succeeded before allowing the player to navigate. Navigation uses the `couponId` from the `play()` response.
- Claim errors are silent. If `POST /game/claim` fails (network error, 500, 503), the frontend logs the error and takes no further action. The player is unaffected.
- The claim request is fired immediately after the `play()` response is received (`setSessionState('revealing')` + fire claim), before the animation completes and before the win screen is shown.

## 4. User Personas

| Persona | Description |
|---|---|
| **PLAYER** | Unaware of the background claim — their experience is: play → win screen appears → tap a CTA |
| **SYSTEM** | Receives `POST /game/claim` with the player's auth token and `couponId`; validates the win; issues the segment coupon via the Coupon API server-side |

## 5. User Stories

- As a **PLAYER who won**, I want my coupon to be automatically prepared so that I never need to tap a "claim" button and never see a loading spinner.
- As a **SYSTEM**, I want to receive a win signal from the frontend so that I can issue the correct segment coupon and associate it with the correct player.

## 6. Requirements

### Functional Requirements

- **REQ-311**: When the `play()` API returns `outcome: 'win'` and a `coupon.id` is present, the system shall immediately fire a background claim request to `POST /game/claim` with the player's auth token and the `couponId`. This request shall be initiated before the win animation completes and before the win result screen is shown.
- **REQ-312**: The `couponId` from the `play()` response shall be stored in memory for the current session and passed to F3.2 for AppLink construction. The claim request response shall not affect or replace this stored value.
- **REQ-313**: The background claim request shall not block rendering of the win result screen, the animation, or any other UI element.
- **REQ-314**: If the background claim request fails (any error — network, 400, 500, 503), the system shall silently discard the error. No error state, no retry, no player notification shall result from a claim failure.
- **REQ-315**: The background claim shall be fired at most once per `play()` session. If the component re-renders or the hook re-runs, a second claim request for the same session must not be sent.

### Security Requirements

- **SEC-311**: The claim request shall include the player's validated auth token in the `Authorization: Bearer` header so the backend can verify the player's identity before issuing a coupon.
- **SEC-312**: The `couponId` shall be held in memory only. It must not be written to localStorage, sessionStorage, or cookies.
- **SEC-313**: The frontend must not call the Coupon API (`POST /segment`) directly. All coupon issuance must go through the project backend.

### Validation Rules

- **VAL-311**: The background claim shall only fire when `outcome === 'win'` and `coupon.id` is a non-empty string. It must not fire for a `lose` outcome or when `coupon.id` is absent.

### Constraints

- **CON-311**: The claim request is fire-and-forget. The frontend must not await its response before rendering the win screen or enabling CTAs.
- **CON-312**: No UI state (loading indicator, error message, disabled CTA) shall be coupled to the background claim's in-flight or completed state.
- **CON-313**: When `VITE_ENV=local`, the claim request must not fire. All game service calls in local mode return mock data; sending a claim with a synthetic `couponId` to a game-api that is not running would fail silently but is unnecessary noise. In all other environments the claim fires normally to game-api.

### Guidelines

- **GUD-311**: The claim request should be initiated in the same async block as the `play()` response handling, so it fires as early as possible — not deferred to a `useEffect` or event handler.

## 7. Acceptance Criteria

- **AC-311**: Given the `play()` API returns `outcome: 'win'` with a `coupon.id`, then a request to `POST /game/claim` is sent before the win animation completes, without any player action.
- **AC-312**: Given the background claim fires, then the win result screen and its CTAs appear without any loading state or disabled state related to the claim.
- **AC-313**: Given the background claim returns a 500 error, then the win result screen remains unchanged — no error message, no retry button, no change to CTA availability.
- **AC-314**: Given the `play()` API returns `outcome: 'lose'`, then no claim request is sent.
- **AC-315**: Given the component re-renders after a win result, then only one claim request is sent for that session (idempotency guard).
- **AC-316**: Given a win result is received, then the `couponId` from the `play()` response is held in memory and absent from localStorage, sessionStorage, and all browser storage.
- **AC-317**: Given `VITE_ENV=local` (game-ui local), when a win result is received, then no claim request is sent — `GameService.claimCoupon()` is a no-op (immediate return) when `environment.isLocal` is true.

## 8. Test & Validation Criteria

**Test Perspectives:**

- **Happy path:** `play()` returns win + couponId → `POST /game/claim` fires in background → win screen appears immediately without loading state → player can tap CTAs freely.
- **Claim failure (500):** Background claim returns 500 → no change to win screen, CTAs remain enabled, player unaffected.
- **Claim failure (network timeout):** Background claim times out → same: win screen unaffected.
- **Lose outcome:** `play()` returns `lose` → no claim request sent (verified via network inspection).
- **Claim fires before animation:** Timing check — claim request is visible in network tab before the animation completes.
- **No duplicate claim:** Component re-renders while claim is in flight → only one request in network tab.
- **Security — no Coupon API direct call:** Network traffic shows no direct call to `coupon-api-*.skylark.co.jp` from the frontend.
- **Security — no storage:** After win result, `couponId` absent from localStorage, sessionStorage, cookies.
- **game-ui `VITE_ENV=local`:** Auth is mocked — a synthetic token `local-dev-token` is used for all game-api calls, including the claim. The claim request still fires to game-api; game-api (with `ENV=local`) is responsible for not forwarding it to the Coupon API.
- **game-ui all other envs:** Full auth flow, claim fires to game-api with real JWT.
- **game-api `ENV=local`:** Game-api mocks integration calls (Coupon API etc.) — claim is acknowledged but no segment coupon is issued.
- **game-api all other envs:** Real Coupon API called on claim.

## 9. Out of Scope

- The mechanics of coupon issuance on the backend (calling `POST /segment` on the Coupon API) — that is SYSTEM's responsibility.
- Surfacing claim errors to the player — failures are intentionally silent.
- Retrying the claim request — no retry logic, no exponential backoff.
- Logging claim events for analytics purposes.
- Displaying coupon details (name, discount amount, expiry) beyond the preview provided in the `play()` response.
