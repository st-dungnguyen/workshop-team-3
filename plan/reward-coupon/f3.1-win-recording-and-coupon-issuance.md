## Design Decision: Merged into POST /game/play

The spec describes a two-call flow where coupon issuance happens in a dedicated `POST /game/win-record` step, triggered when the player taps the claim CTA.

**We merged F3.1 into the existing play flow:**

```
Spec flow (two-call):
  POST /game/play       → { outcome }
  [player taps CTA]
  POST /game/win-record → { couponId }   ← not implemented

Actual flow (single-call):
  POST /game/play → { outcome, coupon? }  ← coupon issued server-side on win
  [player taps CTA]
  window.location.href = AppLink          ← F3.2 navigates immediately
```

This decision is documented in the [epic plan](./_epic-E3-reward-coupon.md#design-decision-single-call-approach) with full rationale.

## Backend: Coupon Issuance in POST /game/play

**File:** `game-api/routes/game/index.js`

Win path in `POST /game/play` handler:

```
1. Verify JWT → extract userId
2. hasPlayedToday(userId) → 403 ALREADY_PLAYED if true
3. Math.random() < winProbability → determine outcome
4. outcome === 'win':
     a. couponService.issueCoupon({ userId, token })
          → POST /segment on Skylark Coupon API (Bearer = user JWT)
          → falls back to mock coupon ID when COUPON_API_URL unset (local dev)
     b. recordPlay(userId, { outcome: 'win', couponId })
     c. return { outcome: 'win', coupon: { id, title, discount, endDate } }
5. outcome === 'lose':
     a. recordPlay(userId, { outcome: 'lose' })
     b. return { outcome: 'lose' }
```

**Coupon metadata source:**

| Field | Source |
|---|---|
| `id` | Returned by Skylark Coupon API (or env var `COUPON_ID` in mock mode) |
| `title` | Env var `COUPON_TITLE` |
| `discount` | Env var `COUPON_DISCOUNT` |
| `endDate` | Env var `COUPON_END_DATE` (defaults to +1 year from server start) |

The Coupon API response confirms issuance but does not provide display metadata. Display data is campaign-level config, set per deploy.

**Error handling in play handler:**

| Coupon API error | game-api response |
|---|---|
| 401 | 401 `unauthorized` (token forwarded from FE is invalid) |
| 503 | 503 `maintenance` |
| other | 500 `systemError` |

When coupon issuance fails, `recordPlay` is NOT called → the player can retry the entire play action. This is safe because the play gate checks `hasPlayedToday` before reaching the coupon step.

**Files:**

| File | Role |
|---|---|
| `game-api/services/coupon.service.js` | HTTP client for Skylark Coupon API (`POST /segment`) |
| `game-api/services/draws.service.js` | In-memory play tracking (`recordPlay`, `hasPlayedToday`) |
| `game-api/routes/game/index.js` | Route handler orchestrating steps 1–5 |

## Frontend: WinResult Component

**File:** `game-ui/src/app/pages/game/containers/GameResult.tsx`

`WinResult` is a sub-component rendered by `GameResult` when `outcome === 'win'`. It receives the full `CouponInfo` object already in memory from the play response.

### State

```typescript
const [ctaState, setCtaState] = useState<'idle' | 'loading' | 'error'>('idle');
```

There is no `'rewarded'` state in the frontend — the spec's `GameSession` state machine is simplified. The play API returns the coupon immediately; the session is effectively "rewarded" once `coupon` is non-null in the result screen.

### CTA Handler

```typescript
const handleCta = async (intent: 'claim' | 'useNow') => {
  if (ctaState === 'loading') return;   // double-tap guard (CON-301)
  setCtaState('loading');
  try {
    if (coupon) {
      const encodedId = encodeURIComponent(coupon.id);
      window.location.href = intent === 'useNow'
        ? `${COUPON_BASE_URL}/app/takeout?coupon_id=${encodedId}`
        : `${COUPON_BASE_URL}/app/coupon/segment?id=${encodedId}`;
    }
  } catch {
    setCtaState('error');
  }
};
```

Navigation is synchronous — `window.location.href` does not throw in practice. The `catch` block covers unexpected failures.

### Coupon Card Display

The coupon card renders within `WinResult` using `coupon.title`, `coupon.discount`, and a formatted `coupon.endDate`. This is not a spec requirement (spec says coupon display belongs to the native app) but is implemented as part of the win result screen for user feedback before AppLink navigation.

```typescript
const formatEndDate = (iso: string): string => {
  const d = new Date(iso);
  return `${d.getFullYear()}年${d.getMonth() + 1}月${d.getDate()}日`;
};
```

## Spec Deviation Summary

| Req | Spec says | Actual |
|---|---|---|
| REQ-301 | Separate `POST /game/win-record` called on CTA tap | Coupon issued in `POST /game/play`; no separate call |
| REQ-302 | Loading indicator while win-record in flight | ✅ `ctaState === 'loading'` disables CTAs |
| REQ-303 | Session transitions to `rewarded` after couponId received | No `rewarded` state; coupon in memory from play result |
| REQ-304 | F3.2 triggered after `rewarded` transition | ✅ AppLink fires on CTA tap |
| REQ-305 | 500/503 from win-record → `reward.claimError` + retry | Not applicable (no win-record call); play 500 shows `game.serverError` |
| REQ-306 | Retry button re-submits win-record | Not applicable |
| REQ-307 | Duplicate-win → treat as success | Not applicable (idempotency handled by `ALREADY_PLAYED` gate) |
| REQ-308 | 401 from win-record → `auth.unauthorized` | Not applicable; auth validated in E1 before reaching result screen |
| SEC-301 | Auth token sent with win-record request | ✅ Token sent with `POST /game/play` |
| SEC-302 | couponId not written to storage | ✅ Held in React state only |
| SEC-303 | Frontend never calls Coupon API directly | ✅ Only game-api calls Coupon API |
| VAL-301 | CTAs active only when session `completed` + outcome `win` | ✅ `WinResult` only renders when `outcome === 'win'` |
